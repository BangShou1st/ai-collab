## R1 [P2] 可恢复失败被主活动归约当成终态

位置：`E:\project\ai-collab\ai-collab-frontend\src\modules\agent\agent-activity.ts:60`，以及 101、122、126 行。

外层 `terminal` 只检查事件类型，任何 `RUN_FAILED` 都被视为终态，没有排除 `retryable=true`。同一运行发生一次暂时失败后，后续模型请求、工具执行、澄清都继续被历史失败遮蔽。

已复现三条实际允许的事件顺序：

1. `MODEL_STARTED → RUN_FAILED(retryable=true) → MODEL_STARTED`：后一次正在分析行为零条。
2. 上述重试成功返回带工具响应，再 `TOOL_CALL_STARTED`：尚在执行的工具被改成 failed，文案为“运行已结束，工具结果需核对”。
3. 重试返回澄清正文，再 `WAITING_FOR_USER_INPUT`：活动区没有等待输入行。

这不是单纯缺少一行重试文案，而是主对话错误描述了恢复后的运行状态。既有“重试后正在分析”测试使用 `RUN_RETRY_SCHEDULED`，没有包含真正自动重试的可恢复失败，因此没有覆盖该问题。

限定修法：主活动归约按事件载荷区分永久失败和可恢复失败；用 sequence 确定时间顺序。暂时失败应结束失败的那次请求等待，不应永久终止后续活动。与原有终态、暂停和等待输入语义一致，不建立第二套后端状态机。

## R2 [P2] 重试行忽略后一次失败和暂停控制

位置：`E:\project\ai-collab\ai-collab-frontend\src\modules\agent\agent-activity.ts:201`、218 行。

`retryActivities` 对每条失败扫描全部后续事件，只要找到过一个 `MODEL_STARTED`，在没有最终终态时就一直将该行设为 running。它没有考虑新一次可恢复失败或暂停，不能区分历史尝试已结束和当前请求仍在途。

已复现：

- `MODEL_STARTED → 暂时失败 A → MODEL_STARTED → 暂时失败 B`：当前已在等待下一次重试，A 行仍显示 running。
- `MODEL_STARTED → 暂时失败 → RUN_PAUSED`：控制说明显示“已暂停”，失败行同时继续承诺“等待自动重试”，与暂停后不自动推进相矛盾。

限定修法：按已排序事件推进展示，明确失败、再次请求、该请求再次失败、等待、暂停/恢复和最终结束。历史行保留历史，不继续表示当前在途；暂停期间不承诺后台会自动重试，恢复后根据真实后续事件继续展示。已有 5 类活动状态够用，必要时加小的展示 helper，不引入前端调度器或通用生命周期平台。

等待澄清、请求完成等既有动作也应纳入同一规则检查，避免保留过期的“正在尝试”。使用已有事实；无法判断具体阶段时采用中性结果描述，不编造实际请求次数或等待倒计时。

## R3 [P2] 超限结果固定声称发生在重试前

位置：`E:\project\ai-collab\ai-collab-frontend\src\modules\agent\agent-activity.ts:209`。

无论后续是否有真实请求，`RUN_BUDGET_EXCEEDED` 都映射为“重试前已达运行上限”。已复现 `暂时失败 → MODEL_STARTED → MODEL_COMPLETED → RUN_BUDGET_EXCEEDED`，请求已实际发出、返回，文案仍说“重试前”。

限定修法：最小方案是采用“运行已达到上限”等不虚构先后因果的文案；若保留阶段区分，必须根据相应事件证据判断。不能因此修改限额或到限续接行为。
