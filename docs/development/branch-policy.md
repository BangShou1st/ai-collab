# 分支策略

## 长期分支只有两个

| 分支 | 角色 | 规则 |
| --- | --- | --- |
| `main` | 稳定发布分支 | 只接受经过代码审查与 CI 全绿的合并；不直接开发、不直接提交 |
| `dev` | **唯一开发分支** | 日常开发、修复、测试与提交**全部直接在此进行** |

## 规则

- **日常开发直接提交 `dev`**（含 Codex/自动化任务），不再为日常任务创建 `feat/*`、`fix/*`、`codex/*`
  等长期远端分支。短生命周期的本地分支可用于临时隔离，但不得长期驻留远端。
- **`dev` 每次 push 都跑 CI**：后端 `mvn verify` + 前端 lint/typecheck/test/build，
  并保留 Docker/Testcontainers「非跳过」守卫（关键真实 PostgreSQL 用例整类跳过即判失败）。
- **审查按 SHA 进行**：上游审查（ChatGPT）直接针对 `dev` 的 commit SHA，不需要额外的功能分支。
- **升级到 `main` 的唯一路径**：`dev` 经代码审查 + CI 验收后，通过 PR 合并到 `main`。
- **绝不自动合并 `main`**：合并动作必须由人明确触发，agent 不代为合并、不代为创建 PR。
- **发布后继续在 `dev` 开发**，不额外保留 `release/*`、`feat/*`、`fix/*` 分支。
- `dev` 通过不代表 `main` 发布：整合到 `dev` 只是完成集成，不构成对 `main` 发布的批准。

## 历史保护

- 已合并过的临时分支在删除前，须确认其提交已经成为 `dev`（或 `main`）的祖先。
- 未被 `main`/`dev` 包含的独有提交，必须先以 `archive/<日期>/<分支名>` 形式的 Tag 归档并推送，
  再删除对应远端分支。归档 Tag 不是开发分支，允许长期保留，用于防止历史丢失。
- 不删除 `main`，不改写历史，不使用 force push。
