## 二、当前 RAG 架构与多调用链分析

当前系统 RAG 整体流程遵循：
`文档解析 (Apache Tika) → 分块 (DocumentChunker) → Embedding 向量化 → pgvector 余弦相似度检索 → 候选集排序 → 来源选择与上下文组装 (KnowledgeContextBuilder) → 引用生成与校验 → 模型回答`

五个具体业务入口调用链细节与差异如下：

| 业务入口 | 入口类与核心方法 | 候选集大小 (Top K) | 来源选择策略 | 来源名额 (Max Sources) | 正文预算处理 | 引用与去重特点 |
| :--- | :--- | :---: | :--- | :---: | :--- | :--- |
| **1. 知识库普通问答** | `KnowledgeQuestionApplicationService.askQuestion()` | Top 8 | `KnowledgeContextBuilder.build()` (贪婪顺序截断) | 5 | 顺序填充，满 2000 code points 截断 | 全局 `contentHash` 去重，跨文档相同条款可能塌缩为单一来源 |
| **2. 知识库流式问答** | `KnowledgeStreamQuestionService.streamQuestion()` | Top 8 | `KnowledgeContextBuilder.build()` (贪婪顺序截断) | 5 | 顺序填充，满 2000 code points 截断 | SSE 事件输出，结构与普通问答保持对齐 |
| **3. Agent 知识检索** | `KnowledgeSearchAgentTool.execute()` | Top 20 | `KnowledgeContextBuilder.buildDiverse()` (两阶段跨文档覆盖优先) | 1~12 (默认 12) | 动态平摊预算（Fair Allowance），防单篇垄断 | 以文档为单位去重，严格保留独立跨文档来源身份 |
| **4. Agent 正文续读** | `DocumentSectionAgentTool.execute()` | 按章节/页码直查 | 确定性文本段落装配，不经过向量检索 | 不适用 | 受 Agent 单次工具上下文上限约束 | 精确还原原文 offset 与段落顺序 |
| **5. AI 任务规划资料** | `TaskPlanningContextAssemblyService` | Top 8~15 | 骨架/细节两阶段资料抽取 | 3~8 | 面向 Schema 结构化装配 | 侧重功能点与依赖声明提取 |

## 四、长文档分块优化实验（针对缺陷 R1）

针对缺陷 R1（长分块尾部信息被长篇前文稀释，导致向量检索直接发生 `DB_MISS`），本轮在测试侧对比了三种分块方案：

### 1. 对照方案定义
- **方案 A（生产基准）**：`TARGET_LENGTH = 1200`，`OVERLAP = 150`；
- **方案 B（语义细分块）**：`TARGET_LENGTH = 400`，`OVERLAP = 60`，按自然段与标点边界切分；
- **方案 C（分段检索 + 相邻扩展）**：在方案 B 基础上检索定位，装配上下文时自动补充相邻段落（`[前文衔接]`）。

### 2. 实验量化指标对照表

| 评估维度 | 方案 A (生产基准) | 方案 B (小分块 400) | 方案 C (分段检索+相邻扩展) | 对比结论 |
| :--- | :---: | :---: | :---: | :--- |
| **尾部条款所在分块长度** | 808 字符 | 166 字符 | 检索 166 字符 / 装配 299 字符 | 方案 B/C 显著剥离冗余前文 |
| **关键条款信号密度** | **3.47%** | **16.87%** (提升约 4.86 倍) | **16.87%** (检索阶段高纯度) | 方案 A 严重被稀释，方案 B/C 信号高度集中 |
| **尾部条款召回表现** | `DB_MISS` (未进 Top 20) | 命中 Top 1~3 | 命中 Top 1~3 | 方案 B/C 彻底解决 R1 漏召回问题 |
| **中部条款信号密度** | 2.36% (1187 字符) | 7.49% (374 字符) | 7.49% (装配 640 字符) | 中部条款有效密度提升 3.17 倍 |
| **总分块膨胀率 (Inflation)** | 1.0x (19 个 Chunks) | **2.16x (41 个 Chunks)** | **2.16x (41 个 Chunks)** | 方案 B/C 分块数量增加 115.8% |
| **Embedding 成本与索引存储** | 基准 (100%) | **+115.79%** | **+115.79%** | 向量库计算和存储成本翻倍 |
| **装配正文预算消耗** | 808 字符 | 166 字符 | 299 字符 (+80.1% vs B) | 方案 C 兼顾语义完整度与预算平衡 |
| **引用定位连续性** | 原生完整段落 | 单句可能缺少上下文 | 包含前后文标记，上下文连贯 | 方案 C 最优，无理解割裂 |

### 3. R1 结论与建议
- **根因确认**：方案 A 的超大目标长度（1200）使长篇运维或重复表格尾部的关键约束被稀释至 3% 左右，导致余弦相似度过低；
- **权衡折中**：方案 B 虽能召回，但带来 2.16 倍的分块膨胀，极大加重向量索引负担；
- **推荐方向**：生产建议采纳 **方案 C 的设计思路**（适度将默认目标分块下调至 600~800，或在后续阶段引入分段检索加按需段落扩展），避免盲目全量激进缩小分块。

### 1. 策略定义
- **策略 A（当前生产）**：两阶段跨文档覆盖优先。第一阶段每个候选文档选出 1 个最佳代表；若名额未满，第二阶段按相似度从剩余候选补齐；

## 七、混合检索可行性与 Reranker 价值评估

执行专项可行性评估测试（产物：`hybrid-search-reranker-assessment.json`）：

### 1. 精确编号检索表现（如 `REQ-7741`）
- **实验表现**：针对包含明确业务编号的查询（`需求变更申请 REQ-7741 的具体授权条款是什么？`），当前 pgvector 余弦相似度直接取得 **Rank 1**（相似度 0.587），精确命中目标分块；
- **原因分析**：Embedding 模型在微调或分词时已将包含大写英文字符与数字的标识符作为强特征聚类，目前纯向量检索对精确编号具有良好召回能力。

### 2. PostgreSQL 原生全文检索（tsvector）可行性
- **原生局限**：PostgreSQL 内置的 `to_tsvector('simple')` / `to_tsvector('english')` 基于空白符与标点分词，**对中文字符串无法进行自然语义分词**，直接使用会将整个中文句子当作单一 token 或单字处理；
- **运维风险**：若要在 PostgreSQL 中支持中文分词，需安装 `zhparser` 或 `pg_jieba` 等外部 C 语言动态扩展，这将严重破坏应用单体部署（Docker）的自包含性、升级兼容性及跨平台稳定性；
- **可行轻量解法**：若未来需要强化特定关键字匹配，推荐在应用层引入针对业务编号（`REQ-`、`TASK-`、`BUG-`）的轻量正则预过滤，或使用 PostgreSQL 内置无需外置词典的 `pg_trgm`（三元组模糊匹配），无需额外安装 C 扩展。

### 3. Reranker（重排模型）价值与成本剖析
- **为什么 Reranker 无法解决 R1？**  
  R1 缺陷是因为超长分块导致信息稀释，向量检索在 Top 20 中**根本没有召回该候选**（属于 `DB_MISS`）。Reranker 仅对已召回的 Top K 进行重排，如果前 20 名没有目标，Reranker 无能为力。
- **为什么 Reranker 无法解决 R2？**  
  R2 缺陷中，目标证据已经进入 Top 8 / Top 20 高排位，丢弃原因在于上下文选择器 `CrossDocumentSourceSelector` 的跨文档代表名额分配逻辑（名额限制与挤占）。无论 Reranker 给它打多高分，名额算法不调整依然会被丢弃。
- **成本收益结论**：  
  引入独立 Reranker 需要引入 Python/ONNX 额外运行环境或调用付费 API，增加 100~300ms 链路延迟与额外内存开销，但**完全无法解决当前已确认的 R1 与 R2 核心问题**。现阶段维持现有轻量纯 Java 架构、不引入外部 Reranker 是正确且经济的选择。

## 九、下一阶段生产优化落地建议

根据本轮充分实验与量化数据，向外部独立审查者及下一阶段工程实现提出 **3 个最小化、低风险且高回报的生产优化建议**：

### 建议 1：将上下文选择策略平滑升级为“保守折中策略 C”
- **动机**：解决缺陷 R2，消除当候选文档数较大时弱代表占满全部名额、挤掉主文档关键高分第二分块的问题；
- **落地改动**：仅在 `CrossDocumentSourceSelector.java` 中调整名额分配：当 `byDocument.size() >= maxSources` 时，第一阶段代表名额上限设为 `maxSources - 2`，保留 2 个名额供全局余下最高分分块竞争；
- **风险与收益**：零数据库迁移，零性能开销；在 E1 用例中证据保留率提升 100%，且通过 E6 严苛回归测试，对现有行为影响极其收敛。

### 建议 2：长文档分块参数精细化调整（TARGET 建议 600~800）
- **动机**：缓解缺陷 R1，在避免小分块膨胀率过高的同时显著提升长文本尾部关键条款的信息密度；
- **落地改动**：将 `DocumentChunker` 的 `TARGET_CHUNK_LENGTH` 从 1200 微调至 700~800，`OVERLAP` 保持 100~120；
- **风险与收益**：无需改造相邻段落拼接算法即可将尾部信息密度从 3.5% 提升至 8%~12%，有效遏制 `DB_MISS`，且分块总数膨胀率控制在 35% 以内，存储与索引压力在可控范围。

### 建议 3：知识库问答上下文构建器引入轻量跨文档去重
- **动机**：消除知识库问答入口在多文档场景下的来源身份塌缩与正文贪婪截断问题；
- **落地改动**：使 `KnowledgeQuestionApplicationService` 逐步复用 `KnowledgeContextBuilder.buildDiverse()`（或提取其文档级去重与动态平摊配额能力），替换原有的全局 `contentHash` 贪婪截断；
- **风险与收益**：提升问答入口在多合同、多版本资料下的来源可追溯性，代码实现逻辑在 Agent 检索中已成熟运行，工程落地几乎零试错成本。
