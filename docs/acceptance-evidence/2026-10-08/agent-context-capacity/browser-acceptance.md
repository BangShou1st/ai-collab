# 浏览器验收证据（bsk，2026-10-08）

环境：本地开发栈，前端 `http://localhost:5173`（vite 代理到本机新构建后端 :8081，profile=local），
生产数据库 `ai_collab`（容器 `ai-collab-postgres`，Flyway 已应用至 v64）。
模型：用户当前 AGENT 配置 `mimo-v2.6-flash-free`（Zen 传输，OpenAI 兼容流式路径）。
登录账号：本地 demo owner。浏览器一律 `bsk`（`--no-focus` 后台会话，未抢用户窗口）。

> 说明：文档上传的浏览器路径被扩展权限拦截（"Allow access to file URLs" 未开启，
> `input` 与 `drop` 两种机制均报 `Not allowed`）。按规则不修改浏览器设置绕过；
> 因此 4 份固定文档改经**同一生产后端 API**（`POST /api/v1/projects/{id}/documents`，
> 携带 Origin 校验头）真实上传，解析与入库走同一条生产链路；Agent 行为验收全部在浏览器完成。

## 场景 1：简单事实查询（不扩容）

- 输入：「项目里当前有几个任务？分别是什么状态？」
- 实测：1 次工具调用（`list_tasks`），无无关扩容；回答给出 3 个任务与状态
  （待处理 2、进行中 1、无阻塞/已完成/已取消），并如实说明三个任务均未分配负责人。
- 诊断区：`Steps 3/64 · Tools 1/64 · 本运行自身（子运行额度独立，不从此处扣减）`；
  `Tokens 输入 17532（累计只统计） · 输出 192（累计只统计）`。

## 场景 2：无文档项目的诚实回答

- 输入：「项目里有哪些文档？简要说明每个文档的内容。」（截图评审项目，无文档）
- 实测：如实回答「当前项目中没有文档」，并说明 `total=0`、已返回全部范围、
  无法为每个文档说明内容——不编造，不把空结果当失败。

## 场景 3：四文档对照（直接研究）

- 前置：项目 `四文档容量验收` 上传 4 份固定文档，全部 `READY`（3/4/4/4 个 chunk）。
- 输入：「对照这四份文档，说明报名容量上限、评分聚合规则、脱敏要求，以及验收标准里的关键阈值。
  要求给出引用来源，并如实说明哪些内容没有读到。」
- 实测：4 步 / 5 次工具调用；正确识别 4 份文档并逐项给出关键事实：
  - 容量：单次导入上限 500 人；验收下限「不少于 200 人、失败率低于 2%」；
    「0.8% 为开发环境实测（1000 人样本），尚未在 500 人并发场景验证」——并标注这是文档记载的缺口而非推断。
  - 评分聚合：去掉最高最低取平均；细则只在技术方案，验收标准只写这一层，两者不矛盾、细则更严。
  - 脱敏：脱敏存储、展示仅显示姓名；AES-256、备份 ≤90 天、日志 1 年只见于规范文档。
- 引用：`来源（15）`，含 filename/heading/quote；逐条可溯源到具体文件与章节。
- 诚实缺口：明确写「四份文档均未通读全文：所有引用来自语义检索片段
  （coverage=RELEVANT_EXCERPTS_ONLY），没有读取任何文档的完整正文或提纲；
  各文档未被检索命中的章节我没有看到，不能声称"全文没有"某个内容」。
- 诊断区：`Tokens 输入 38528（累计只统计） · 输出 2905（累计只统计）`。
- 说明：模型选择了**直接检索**而非委派——设计明确"不强制委派、子调用率不是质量指标"，
  这不是缺陷；委派路径由场景 4 单独验证。

## 场景 4：四文档逐份委派（显式要求委派）

- 输入：「请用委派方式（delegate_document_research）分别深入研究这四份文档，逐份给出完整正文要点与引用，
  并列出每份文档未读到的部分。」
- 浏览器实测过程：
  - 模型第一次把 4 个委派放进同一批，被 `DELEGATION_BATCH_LIMIT` 正确拒绝（委派须单独成批）；
  - 随后逐份委派，3 个子运行成功；第 4 次委派因 `maxChildren=3` 已满，工具在该轮**不再暴露**，
    模型收到 `TOOL_NOT_ALLOWED`（工具未在本轮暴露），随即**改用本层工具直接读取第四份正文全文**并完成目标。
- 数据库复核（生产库，只读查询）：
  - 父运行 `f1e207f4`（v2，64/64）：`children_used=3/3`，`SUCCEEDED`；
  - 3 个子运行（v2，16/24）全部 `SUCCEEDED`；
  - `DELEGATION_COMPLETED`：3 条，citations 3/4/4 条，`coverage.coverageKnown=true`，child_status=SUCCEEDED；
  - 父最终回答明确、如实地分区说明：「前三份已有委派子运行结果（SUCCEEDED，覆盖块经持久化工具结果校验：
    各文档提纲已取得、正文各节全部读完、无未闭合分页截断、已知覆盖缺口为无）；
    第四份的委派调用本轮被拒（TOOL_NOT_ALLOWED），为完成目标我改用本层工具直接读取了它的正文全文
    （chunk 0 读到 chunk 3，hasMore=false、truncated=false、readChars=326），与提纲 4 节一一对应」；
    并逐份给出要点、引用与"未读到"汇总。

## 场景 5：刷新与跨页恢复

- 完成运行后离开会话页（工作台 / 项目列表），再返回 Agent 工作区：
  会话、模型、执行过程、最终回答与查询事实完整恢复；状态标签为「Agent 已完成」；
  不重复发起新运行，也不出现"继续"按钮。

## 结论

- v2 新策略在真实浏览器链路下可用：累计 token 只统计并如实展示（不展示假的剩余额度/百分比），
  步骤/工具标明为本运行自身计数，64/64 与 16/24 的独立执行额度按策略生效。
- 简单问答不为扩容增加无关调用；固定四文档能取得完整正文与准确引用，未覆盖部分如实列出。
- 委派链路（受理 → 子运行 → 回收 → 父综合）与批限/子数量上限、可见性收窄、
  拒绝后改走直接取证、零交付防护全部按设计工作。
- 无文档/未读范围诚实说明；未出现把 SUCCEEDED 等同于全文覆盖的表述。
