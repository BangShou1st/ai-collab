## 一、第一轮必须交付什么

不要只回复“我先看一下”或给一个计划就结束。先读取必要文档和生产源码，第一条完整答复要向我讲清楚**目前 AI 是怎么设计、怎么实现、做到哪一步了**。

我既想知道用户能用什么，也想从程序员角度理解实现。请用清晰的分段、必要的表格和一张核心调用图说明：

1. **项目进度总览**：已有并验收、已有但有支持边界、尚未实现/可选研究分别是什么。不要把测试数量等同于产品质量，也不要把历史验收说成本轮实测。
2. **AI 能力全景**：Agent、模型配置与适配、上下文与摘要、文档索引/RAG、独立知识问答、任务规划、审批写入、前端展示分别怎样协作。MCP 等扩展若在代码中存在，也交代接入位置、范围与验证程度；统计或洞察页面是否调用模型要核实，不能见到“AI”标题就算 AI 能力。
3. **一条用户请求的完整流程**：从前端发送、会话/运行创建、后台租约领取、请求准备、模型返回、工具执行到最终回答。解释关键类调用关系和数据落在哪里。
4. **模型怎样动态切换**：当前配置解析、请求快照、Native/Legacy 模式、在途请求与下一轮的边界。
5. **模型到底看到哪些内容**：系统提示词、Skill、当前目标、更正、页面上下文、近期消息、旧摘要、工具结果如何选择和组织；哪些是可信业务状态，哪些是模型输出。
6. **预算是什么、到限怎么办**：区分单次上下文容量、运行总额度、请求超时、执行时长、步骤/调用上限、token 记账和钱。讲清当前策略、参数来源和真实限制；RAG 不等于自动扩大模型窗口。
7. **摘要与 RAG 的具体实现**：摘要触发、覆盖、提交、防丢信息和失败处理；上传文档到向量检索、来源引用的完整链。说明二者解决不同问题。
8. **稳定性与恢复**：可恢复失败自动重试、进程崩溃接管、已保存结果消费、工具幂等、主动暂停、输入续跑、取消、终态派生重试有哪些不同。
9. **规划与业务写操作**：Agent 调用规划入口与独立后台规划的关系；权限、审批、generationSeq/attemptId、版本提交、迟到结果隔离怎样保证正确。
10. **前端体验及流式链路**：自然语言过程说明、工具活动、最终回答、自动重试、暂停、SSE 持久事件、临时正文预览、刷新恢复分别怎样实现。
11. **维护质量判断**：现在的职责边界哪里清楚，哪里仍有实际耦合；用具体代码和修改传播范围证明，不能只凭文件长、行数多就判过度设计。
12. **下一步**：只排最值得做的 1–3 件事，说明用户收益、当前证据、最小范围、是否现在需要做以及何时结束。

## 二、我的需求与长期取舍

- **满足使用需求，切忌过度设计。** 更在意回答有用、资料完整、操作可靠、交互顺畅，而不是抽象数量、代码行数或功能清单。
- 失败自动重试、崩溃恢复、暂停/续跑是重要基础能力，不能为了精简把它们删掉。
- Agent 中途可以换模型，**以用户当前配置为准，下一次请求生效**；不能把运行一开始的模型锁死，也不要默认引入自动择模。
- 暂停后通过输入“继续”等明确表达恢复，**不需要继续执行按钮**。现有识别是保守的确定性分流，不是任意语言都能理解的智能恢复。
- 暂停 Agent 的后续动作，**已受理的后台规划继续完成**；恢复时读取其真实结果。暂停是动作边界暂停，不承诺强制立即中断已发出的模型请求。
- 前端要自然、清楚、美观：过渡说明、真实工具活动、最终结论有层次，避免主界面只输出赤裸的工具名；诊断和原始名称放技术详情。
- 精确 token 计费不是当前重点。保留必要用量事实、上限和防重复记账，不继续围绕计费边角无限收尾。预算仍有防超限、防循环和控制资源的作用。
- 我曾担心自编排维护成本、考虑框架；目前决定**先把现有实现维护好**。没有明确收益证据前，不默认迁移 Spring AI/LangChain4j/LangGraph，不叠加第二套循环、状态或检查点。代码量多少不是决策目标。
- 维护看高内聚、低耦合、依赖明确、唯一职责入口、修改时需要理解多少边界；不要为了这些口号继续拆文件、加接口和配置。
- 可以认真参考 `E:\project\LangChain_Official_Course`，尤其 `lca-lc-foundations`；**借鉴思路**，不能机械复制 Python 课程，也不能把教学 InMemorySaver 当成生产持久化方案。
- 不要把每轮报告末尾的“建议下一步”自动升级为我的需求或验收门槛。已收口能力除非出现新的可复现高价值缺陷，否则保持收口。

## 五、当前设计骨架与已完成工作

### 1. 基本架构和执行主线

后端为 Java/Spring Boot，前端 Vue/TypeScript；Agent 是现有业务系统内的自编排实现，没有引入另一套 Agent 框架作为执行主体。持久业务事实主要在 PostgreSQL，文档涉及 MinIO、Tika、embedding 与 pgvector。其他基础设施实际承担什么职责，请据源码解释。

`AgentRunService` 受理输入，保存 session/run/message/working_state 等；`AgentRuntimeJob` 通过租约领取运行，`AgentWorker` 调 `AgentRuntimeCoordinator.advance` 推进。运行状态、步骤、工具 invocation、提案、消息、事件共同形成可恢复事实，不以 JVM 内存栈作为恢复依据。解释状态机、租约、版本/CAS各自的作用。

M1–M4 已做有限维护：`AgentRuntimeConfiguration` 统一生产装配；协调器显式注入消息组装器、工具执行器、摘要器；工具执行用 `AgentToolScheduler` 的专用池/限流；工具结果投影独立为 `AgentToolOutputProjector`；删除无消费者旧入口；domain 不再反向依赖 application。不要把这些重新列为待开发。

### 2. 配置、模型和协议

`RoutingAgentModelExecutor.resolveRequest` / `AgentModelConfigurationStore` 按 requester + AGENT 用途解析当前配置（用途分配优先，否则默认）。同一份 `ResolvedRequest` 贯穿本次能力判断、窗口预算、提示词模式、工具暴露、出站调用与响应校验；`AiConfigurationContext` 把快照带入出站层。已发出请求按原配置完成，下一请求用新配置。禁用/删除明确失败，不偷偷换另一个模型。

原生工具模式用 `NativeToolCallingExecutor`，CHAT-only 兼容路径用 `LegacyReadOnlyAgentExecutor` 的决策解析，只读能力边界保留。恢复旧批次按落库 `source_mode` 校验，不能拿新模型的模式重新否定旧提案。解释提供商适配与 Agent 决策职责的边界，不把协议适配误写成独立编排。

### 3. 工具、Skill 和资料完整性

Skill 提供任务要求/工具白名单等，通用提示词由 `AgentModelMessageComposer` 组织；Skill 的参考步骤不等于已经执行。工具注册与执行校验仍以服务器权限、Schema、资源范围为准，不能让模型决定授权。

`AgentToolCallExecutor` 负责批次校验、已完成 invocation 复用、只读并行、写/审批串行、结果落库。规划受理与审批服务复用原业务边界。`AgentToolOutputProjector` 只负责模型可见投影，不读数据库、不决定下一步；过期判断留在组装器查询边界。

`ListPageContract` 对齐服务端与模型可见分页：nextCursor 是第一条未返回记录，续读 id>=cursor；可见记录、returned/total/hasMore/nextCursor/taskFacts 必须一致。任务/里程碑分页、长输出投影已有串联回归。模型是否主动续读仍有行为差异，不能把分页可用等同于每次分析都覆盖全部资料。

### 4. 上下文、工作状态与摘要

`AgentContextAssembler` 组织可信项目/权限/页面上下文；Composer 从 working_state、近期消息、旧摘要和工具结果中选择内容，并保护当前请求与有效约束。讲清上下文不是把整个项目一次塞进模型。

`AgentWorkingState` 的约束只从用户消息进入，来源 quote 保留，不让助手推测变成硬约束。DATE_LOCK 单字“别”误匹配“分别”的缺陷已修。显式更正保留原文/sourceMessageId；全部 active 更正按时间顺序给 Composer 和摘要；“新目标：”使旧更正退位。**更正不会被脆弱语义解析直接改写 activeGoal**，而是读取端明确声明冲突时用户更正优先。

`AgentContextSummarizer` 是有界增量摘要：确定性压缩后仍有旧内容放不下才尝试；旧摘要完整参与下一次摘要，长消息按 ID+偏移记录覆盖，不虚报已读完；提交校验 stateRevision/goalRevision 等，生成期间不持有数据库行锁；失败/CAS 冲突可降级，摘要不调用业务工具。默认输入/输出字符上限等参数应从源码解释，不能把摘要理解成无条件删除历史。

真实 29 轮验证已经证明：旧原始消息退出窗口后，摘要进入后续请求并保留更正后的目标。当前摘要可用，不需要只因为框架有现成组件就替换；若要评价更复杂会话的摘要质量，需要具体样例。

### 5. 预算与到限行为

`AgentContextProperties` / `AgentContextBudget` 管单次输入：已知模型窗口扣除输出预留/安全余量，再与运行剩余额度、应用单次上限取最小；未知窗口用应用限额兜底。已有 window-overrides 是可选接入信息，未决定建设逐型号策略/动态校准体系。

运行另有输入/输出额度、步骤/工具上限、执行时长与请求 deadline；`AgentConvergencePolicy` 做继续/收尾/耗尽判定，`AgentLoopGuard` 防重复循环。降级重组仍装不下当前请求时明确终止，不发一个丢了目标的请求。解释到限时目前怎样保存已有结果、提供部分回答或终止，必须根据具体路径说明。

token 用量与调用身份仍有原子、幂等结算契约；这是现有基础事实，不等于精确费用产品。本轮不继续研究计费边角。

### 6. 自动重试、崩溃恢复和暂停续跑

可恢复失败复用既有错误分类、retryCount/retry_after/FAILED_RETRYABLE 等机制；前端展示按持久事件推导。真实等待重试、请求在途、暂停、再次失败、恢复完成各有边界：失败或完成关闭该次请求，新的 MODEL_STARTED 才再次表示在途。

崩溃接管计时使用 V60 `last_progress_at`：只累计持久证据确认的执行段，不把租约等待、排队、离线当执行；未确认尾段不声称精确计量。

已保存且未消费的纯文本/工具响应先于新的模型准入检查消费，共用 `afterResponseSaved`；`finalizing` 随响应持久化，恢复不按变化后的计数重新推导；结果消费与收口原子完成。工具按 invocation 身份、名称/参数一致性复用，恢复总额度只计尚需执行项，source_mode、权限、白名单、审批不绕过。业务防重复有明确范围，不宣称对任意外部副作用普遍“恰好一次”。

V61 暂停：RUNNING 只登记 pause_requested_at，不因暂停意图 bump version 破坏在途结果落库；worker 在动作边界确认 PAUSED，保留未消费响应与 PENDING 调用，释放租约；模型、摘要、工具和业务受理均有准入检查。暂停不清零额度，已受理后台规划继续。明确续跑经 `ResumeIntentRecognizer` 和 submit 恢复原 run；绑定控制输入不会误建新任务。

不要混淆三种情况：同一 run 的崩溃恢复、同一 run 的 PAUSED→QUEUED、终态手动重试派生新 run。现有 FAILED/CANCELED/BUDGET_EXCEEDED 手动重试保留旧历史、创建幂等派生运行并重置运行额度；**跨运行的剩余工作到限续接仍未实现**。

### 7. 文档/RAG、知识问答、后台规划

真实文档链已跑通：上传→Tika 解析→分块→真实 embedding→pgvector→`DocumentSearchService`→Agent 的 `search_project_knowledge`→工具结果→带来源回答。真实证据使用 `qwen3-embedding:0.6b` /1024 维；这只是验收模型，不是产品固定模型。之前 embedding 失败根因是 Ollama 服务未启动，不是链路缺陷。

独立知识问答在 `knowledge/application/service`（包括普通和流式问答服务）复用文档检索与模型网关，并有会话、引用校验和持久化逻辑。它与 Agent 是否共享哪些上下文/网关，应读取源码说明，不能把两种入口混为一个。

任务规划在 `planning/application`，重点 `TaskPlanGenerationOrchestrator`、`TaskPlanVersionCommitService`、局部修复/确认/恢复服务：蓝图/详情异步生成、结构验证/修复、版本管理与人工确认。旧详情结果提交绑定真正所属的 generationSeq + attemptId + 阶段，防取消后重生成时旧结果借新身份污染。READY 不等于已创建业务任务，具体确认事务应据代码解释。现有历史规划质量证据不冒充最新重跑；字段级错误反馈的真实触发限定也应保留。

### 8. 前端与流式/SSE

Agent 主线为用户问题→自然语言过程说明→真实工具活动→最终回答。正文为空不编造过渡文字；最终回答出现一次，Markdown 经 marked+DOMPurify。工具原名与错误诊断可折叠；连续查询可分组；向上读历史不被强制滚动；活动块按 runId 稳定，刷新/事件重放不重复。

临时正文链：`ModelContentPreview` 观察者（跨读流线程显式捕获）→适配器累计正文→`AgentContentPreviewPublisher`→既有 SSE 的 MODEL_CONTENT→前端预览。帧含 modelCallId/revision/text/final，自包含、可合并、有 8000 字符展示限额；不落库、不占持久序号、不更新 Last-Event-ID、不重放。完整响应仍按原链落库/执行，最终以持久消息收口。前端只让被时间线接受的事件推进预览，迟到普通帧被请求关闭边界拦住；[QUESTIONS] 不作为正文显示。

实时增量目前只覆盖 **Zen 的 OpenAI 兼容生产路径**；Custom 非流式、Anthropic/Gemini、Legacy 保持一次完成展示。真实最终回答轮 48 帧（47 增量+1 final），全运行 51 帧；真实 SSE 与合成 UI 的证据边界不同，不能说所有 provider 都已逐字流式验收。

`AgentEventStreamService` 已统一 replay/持久事件/临时正文/heartbeat 的显式网络写到共享有界池（4 worker+128 队列），每订阅单飞；业务/模型读流/afterCommit/scheduler 只唤醒。持久事件按数据库游标有序追赶，预览可丢、持久游标不随预览推进。L1 读取异常不自旋、L2 登记/摘除原子化已独立复核通过，**本批可以结束**。

前端订阅、控制回包、消息加载按项目/会话/恢复代次等核对，防切会话与 A→B→A 迟到响应覆盖视图。当前 SSE 是进程内订阅能力，不冒充多实例总线。
