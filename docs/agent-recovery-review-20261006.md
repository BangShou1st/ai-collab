## 1. 已保存最后一轮回答被新的请求准入判限覆盖

源码入口：

- `AgentRuntimeCoordinator.java:192–209`：先计算收敛模式，EXHAUSTED 时返回兜底或预算终态，然后才查询待消费结果。
- `AgentConvergencePolicy.java:29–47`：模型轮次达到上限、剩余步骤不足等都会判为 EXHAUSTED。
- `AgentRunEventRecorder.java:603`：保存 MODEL_TURN 已增加步骤数；收敛策略也会看到新增模型轮次。

确定性现场：ITERATION_PLANNING 上限为 8 次模型请求。已有 7 轮模型与成功查询，正常路径在请求前判为 FINALIZE；第 8 轮完整文本已保存，尚未收尾时退出。接管看到模型轮次已经是 8，先进入 EXHAUSTED，把完整答案替换为“模型未能在本次运行预算内生成完整总结……”的工具证据兜底。

实际输出：

```text
PROBE_CAP before=FINALIZE after=EXHAUSTED recovered=BUDGET_EXCEEDED savedAnswerRetained=false modelCalls=0
```

正常路径仍使用发出第 8 次请求前的 FINALIZE 意图；核心动作没有待完成要求时，已有文本应按原规则成功收尾。恢复一个已保存结果，不需要再预留“两步完成下一次模型请求与最终回答”。

## 2. 恢复路径遗漏已保存响应的实际输入超限保护

源码入口：

- 正常路径 `AgentRuntimeCoordinator.java:419–427`：保存响应后检查 `inputTokensActual`，实际超出有效上限则预算终止，不执行该响应的工具、不记成功。
- 恢复路径 `AgentRuntimeCoordinator.java:204–209`：直接调用工具执行器或文本收尾，没有同一检查。
- `AgentConvergencePolicy` 没有统一的实际输入超限检查，不能替代上述保护。

确定性现场：第一个模型文本响应已保存，输入上限 50000、实际累计 50001，没有成功工具证据；在正常路径检查超限前退出。接管收敛模式为 CONTINUE，直接发布文本并记为 SUCCEEDED。

实际输出：

```text
PROBE_INPUT cap=50000 actual=50001 recovered=SUCCEEDED savedAnswerPublished=true modelCalls=0
```

这是执行限额保护的一致性问题，不是精确计费的新任务。正式回归需要覆盖纯文本和带工具调用两种响应；后者应确认没有新增工具执行或业务写入。

## 3. 原请求的强制收尾意图没有可靠持久化

源码入口：

- `AgentRuntimeCoordinator.java:267–275`：准备请求时，`needsFinalRequest` 还可以把 `finalizing` 从 false 改为 true。
- `AgentConvergencePolicy.java:70–82`：这一判定依赖下一次输入估算、输出预留和剩余预算，不只依赖 `decide` 的模式。
- 恢复路径只重新调用 `decide`，没有原请求的最终 `finalizing` 值。
- `completeTextTurn` 注释所称“重新推导得到与正常路径一致的结果”因此不成立。

确定性现场：目标为“请生成迭代规划草稿”，已有 5 次成功背景查询，尚未调用 `start_task_plan`；输出累计 17500、上限 20000，剩余 2500 小于输出预留 4000。`decide` 为 CONTINUE，但正常请求准备的 `needsFinalRequest` 为 true，实际发出的应是收尾请求。保存“只完成了背景核对，规划草稿尚未生成。”后退出，接管重新 `decide` 仍为 CONTINUE，因此把本应 BUDGET_EXCEEDED 的部分完成记为 SUCCEEDED。

实际输出：

```text
PROBE_PHASE before=CONTINUE needsFinalRequest=true after=CONTINUE coreAccepted=0 recovered=SUCCEEDED modelCalls=0
```

模型轮次、步骤和预算累计本身也在响应落库后发生了变化，不能把请求后的重新计算当作请求前意图的快照。
