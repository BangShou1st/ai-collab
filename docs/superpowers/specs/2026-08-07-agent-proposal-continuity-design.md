# Agent 提案连续性与确定性交付设计

## 1. 背景与根因

当前 Agent 的写工具只创建审批提案，并把 Run 停在 `WAITING_FOR_APPROVAL`。模型还可能仅在自然语言中声称“已提交审批”，却没有真实调用写工具。跨轮次继续对话时，运行时主要依赖截断后的消息和步骤文本，缺少结构化的“当前提案最新版本”上下文，因此无法可靠处理负责人、日期、里程碑等字段的补充和冲突覆盖。

用户看到的 `#29` 是 Run 事件序号，不是二十九轮上限。该案例在最后一次模型调用后进入 `RUN_FAILED`，符合收敛阶段得到空内容或不合规最终响应时触发 `AGENT_INVALID_RESPONSE` 的现有行为。只提高预算或修改 Prompt 不能解决虚假交付、提案不可见和跨轮次冲突。

## 2. 目标

- 所有 Agent 审批写工具在提案真实持久化后，立即向用户返回可验证的结果摘要并正常结束 Run。
- 同一会话、同一业务意图的待审批提案可以持续修订；最新明确需求覆盖旧值，未提字段继承。
- 已批准提案后续通过真实资源的更新提案修改；已拒绝或过期提案不再复用。
- 刷新、Worker 重启或新 Run 不丢失当前提案上下文。
- Agent 只有在存在真实工具或审批证据时才能声称已创建、提交或更新。
- 收敛边界已有可交付证据时返回确定性保底结果，不把可用运行错误地标记为失败。

## 3. 非目标

- 不取消人工审批，不允许模型批准自己的提案。
- 不扩大现有业务角色权限，不绕过项目状态、资源版本或服务端校验。
- 不在本次增加新的业务资源类型或新的外部 MCP 写能力。
- 不用无限模型轮次或无限工具预算掩盖收敛问题。
- 不依赖前端临时拼接来替代后端持久化回答。

## 4. 方案选择

采用“持久化提案上下文 + 通用修订器 + 确定性交付”。

未采用仅增强 Prompt 的方案，因为模型上下文会被截断，且自然语言不能承担并发、版本和审计语义。未采用仅由前端显示审批事件的方案，因为 API、刷新恢复和其他客户端仍会缺少正式回答。未采用提案后再次调用模型总结的方案，因为它保留了空响应、重复工具调用和预算边界失败。

## 5. 可信上下文与冲突规则

每个新 Run 的可信上下文按以下优先级组装：

1. 当前用户消息中的明确要求。
2. 当前会话内相关待审批提案的最新完整参数。
3. 已批准提案的执行结果和真实资源 ID。
4. 已持久化的历史用户消息、工具结果和审批修订记录。
5. Agent 之前的自然语言回答。

自然语言回答不作为业务事实。服务端向模型暴露结构化提案摘要，包括审批 ID、资源类型、操作类型、状态、版本、当前完整参数、执行结果和最近差异。

参数合并采用字段存在性语义：

- 新请求中存在的字段覆盖旧值，包括显式 `null`。
- 新请求中不存在的字段继承旧值。
- 嵌套的 `changes` 对象按同一规则逐字段合并。
- 合并后必须重新经过目标写工具的 normalize、Schema、Bean Validation、项目归属和业务规则校验。
- 模型不得通过省略必填字段删除旧值，也不得通过空字符串代替 `null`。

## 6. 通用提案标识与匹配

审批记录增加服务端生成的提案元数据：

- `session_id`：限定对话范围。
- `proposal_family`：稳定的资源与操作族，例如 `TASK_CREATE`、`TASK_UPDATE`、`MILESTONE_CREATE`、`MILESTONE_UPDATE`、`MEMORY_CREATE`。
- `subject_key`：服务端规范化的意图主体；更新操作使用资源 ID，创建操作使用首次提案生成的稳定 UUID。
- `revision`：从 1 开始递增。
- `superseded_at`：仅用于明确被替代的历史提案，不替代 `REJECTED`、`EXPIRED` 等审批状态。

所有写工具通过统一接口提供 `proposalFamily`、目标资源标识和参数合并能力，不在 Runtime 中为任务、里程碑或记忆写分支判断。

关联规则：

- 用户或模型携带 `approvalId` 时，服务端必须验证它属于同一项目、同一会话、同一请求人、状态为 `PENDING`，且工具族兼容。
- 未携带 `approvalId` 且同一会话只有一个兼容的 `PENDING` 候选时自动关联。
- 存在多个兼容候选且当前消息无法唯一确定主体时，不做猜测；返回一个聚焦问题，并列出最小必要选项。
- 明确是独立新需求时创建新 `subject_key`，不能只按工具名合并。

## 7. 提案生命周期

### 7.1 待审批

对 `PENDING` 提案的补充或冲突要求执行原位修订：审批 ID 保持不变，完整参数、参数哈希、差异、过期时间和版本更新，`revision` 递增。每次修订写入不可变的修订历史，记录修订前参数、修订后参数、差异、来源 Run、请求人和时间。

### 7.2 已批准

批准后执行正式 Application Service，结果中保存真实资源 ID 和版本。后续修改不得改写已批准审批；应创建对应资源的更新审批，并以批准结果中的真实资源 ID 为目标。若资源类型没有更新工具，则明确告知当前不能修改，不伪造交付。

### 7.3 已拒绝或过期

`REJECTED` 和 `EXPIRED` 提案视为已弃用，不参与自动匹配。用户再次提出需求时创建新审批 ID 和新 `subject_key`。

## 8. 事务、并发与权限

- 使用下一个可用 Flyway 版本新增提案元数据和不可变修订表；当前工作树已有 V35、V36，因此实现时使用 V37，不修改既有迁移。
- 提案创建或修订在单个数据库事务中完成，并锁定目标审批行。
- 修订使用 `version` CAS；并发新消息只有一个成功，失败方重新读取最新版本并重新合并，不能静默覆盖。
- `(project_id, session_id, id)` 和资源 ID 查询必须显式包含 `project_id`。
- 创建和修订只要求当前项目成员；批准和拒绝继续要求项目管理员。
- 批准时继续锁定审批、校验 nonce、幂等键、项目状态、当前角色、资源版本和业务前置条件。
- 模型调用不进入数据库事务。
- Prompt、完整模型输出和业务正文不进入日志或审计。

## 9. Run 状态与确定性交付

写工具成功创建或修订审批后，Runtime 不再安排额外模型轮次：

1. 持久化工具结果和审批/修订。
2. 追加 `APPROVAL_REQUESTED` 或新的 `APPROVAL_UPDATED` 事件。
3. 根据审批真实数据生成确定性中文摘要，保存 assistant message。
4. 追加 `RUN_SUCCEEDED`，将 Run 置为 `SUCCEEDED`。

审批生命周期与 Run 生命周期解耦。管理员对 `PENDING` 审批执行批准或拒绝时，不要求关联 Run 仍为 `WAITING_FOR_APPROVAL`，也不重新把已结束 Run 放回队列。取消的 Run 不影响已经完整提交的审批；未完成事务不会留下半条提案。

确定性摘要至少包含操作、资源标题或类型、关键变更、当前审批状态和审批 ID。不得包含 nonce。创建和修订的措辞必须区分“已生成提案”“已更新提案”和“已批准并写入”。

## 10. 收敛与失败语义

- 有成功只读工具证据时，收敛边界生成基于证据的保底回答。
- 有成功审批创建或修订证据时，直接使用确定性提案摘要。
- 只有模型调用失败、权限/业务校验失败、数据库事务失败，或没有任何成功证据且模型响应非法时，Run 才失败。
- `AGENT_INVALID_RESPONSE` 不得覆盖已成功产生的可交付结果。
- 事件 `sequence` 仅表示有序流水号，不作为模型轮次或步骤预算。

## 11. API 与前端

后端 Run 详情和审批 View 返回提案族、修订号、来源会话、最新差异和可安全展示的参数。OpenAPI、Java View、TypeScript 类型和 API 封装同步更新。

前端在同一次事件流中展示 assistant 最终回答和审批事件，并刷新审批列表。审批卡显示当前修订号、最新字段和差异；旧修订只用于审计，不显示成多个待审批卡。页面刷新后通过消息、Run 和审批 API 恢复相同状态。

`WAITING_FOR_APPROVAL` 仅保留为旧数据兼容状态，新写提案 Run 不再以该状态作为正常终点。已有待审批记录仍可批准或拒绝。

## 12. 现有写工具覆盖

首个实现必须同时覆盖：

- `create_task_after_approval`
- `update_task_after_approval`
- `create_milestone_after_approval`
- `update_milestone_after_approval`
- `create_memory_after_approval`

会议转任务可能一次产生多个独立任务提案，每个任务使用不同 `subject_key`。项目迭代规划可自动修订唯一兼容提案。项目记忆当前只有创建工具；已批准记忆的后续修改在缺少审批更新工具时必须明确报告能力边界。

## 13. 测试与验收矩阵

### 后端领域与仓库

- 待审批提案的新增字段覆盖、已有字段覆盖、显式清空和未提字段继承。
- 同一审批 ID 修订时 `version`、`revision` 和修订历史递增。
- 已批准后创建更新提案；已拒绝或过期后创建新提案。
- 单候选自动关联、多候选拒绝猜测、独立创建不误合并。
- 跨项目、跨会话、跨请求人 approvalId 被拒绝。
- 并发修订不丢失最新明确要求。
- 批准已结束 Run 的待审批提案成功且不重新排队 Run。

### Runtime

- 五个写工具创建或修订后都保存回答并返回 `SUCCEEDED`。
- 没有审批证据时不能输出“已提交/已创建/已更新”。
- 模型在最终轮返回空内容但已有工具证据时使用保底回答。
- 完全无证据的非法响应仍返回稳定失败码。
- 事件序号超过 29 不影响运行。

### 前端与契约

- 同一事件流显示最终回答和待审批卡。
- 修订后只显示一个审批卡及最新版本。
- 刷新后恢复消息、审批和版本。
- OpenAPI 校验、TypeScript 类型检查和错误中文映射通过。

### 真实验收对话

至少执行以下类别而非只复现固定文案：

- 创建后补负责人、改负责人、改日期、清空日期、改优先级。
- 同时存在两个待审批任务时明确修改其中一个。
- 拒绝后再次提出相同需求。
- 批准创建后再修改正式资源。
- 一次会议生成多个任务且互不覆盖。
- 里程碑和项目记忆提案重复上述适用场景。
- 模型在预算边界或空最终响应时仍返回已有交付。

## 14. 交付拆分与 Claude–MiMo 边界

这是中大型、跨模块且涉及迁移、状态机、事务和 API 的改动，必须由 Claude 主导并承担最终验证。

Claude 必须完成：

- 失败复现、状态机和数据模型设计。
- V37 迁移、约束、锁、CAS 和事务实现。
- 通用提案修订接口、Repository、Service 和 Runtime 集成。
- Approval 批准/拒绝与 Run 解耦。
- OpenAPI 与跨层契约决策。
- MiMo 输出逐行审查、集成测试、全量验证和真实对话验收。

MiMo 仅可在 Claude 给出完整签名、断言和允许文件后承担：

- 单个 Java DTO/View 或单个 TypeScript 类型文件。
- 单个事件/状态中文映射。
- 已由 Claude 指定输入输出的纯参数覆盖函数及其单测。
- 已给出完整断言的单个前端组件测试或局部样式。

MiMo 禁止修改迁移、审批 Repository/Service、Runtime、状态机、权限、事务、OpenAPI 或 Git，也禁止根据测试失败自行改变断言。

## 15. 完成标准

只有同时满足以下条件才可交付：

- 所有行为矩阵测试通过，且至少一个回归测试在修复前按预期失败。
- 后端全量测试和打包、前端测试/类型检查/构建、OpenAPI 校验、`git diff --check` 全部通过。
- 真实数据库和 HTTP 链路证明提案创建、修订、批准、拒绝和刷新恢复。
- `docs/feature-matrix.md`、`docs/development/guides/planning-and-agent.md`、`docs/api/openapi.yaml` 和 `docs/database.md` 与代码一致。
- 验证报告列出实际命令、退出码、测试数量和任何环境限制。
