# Skill / Tool 边界设计与下一轮开发范围

> 日期：2026-10-07。研究基线：`codex/context-foundation` / `00a85fe43ffed3b7fe6bdff4a5575b10472859c0`。
> 本文是继续研究后的设计建议，不是已实现变更或已通过验收的声明。本轮只编辑文档，不修改生产代码、不调用模型、不重跑测试。
> 系统全景与恢复/业务事务契约见 [Agent 系统现状与维护记录](agent-system-research-and-roadmap-20261007.md)。本文收窄到 Skill、Tool、运行策略及下一轮开发，不重开已收口的 SSE 发送层。

## 1. 结论

当前 Skill 与 Tool 在接口上已分开，但职责契约没有完全对齐，值得做一次有限设计与实现整理。

不是“没有 Tool”，也不是“六个 Skill 都应改成 Tool”。真正的问题是：部分 Tool 给模型的参数说明不完整；Skill 同时承担任务提示、输出模板和可用工具边界，自动关键词选择又把这些绑在一起；有些 Skill 元数据不像 Tool Schema 那样实际参与自由对话调用。

建议下一轮开发两个交付物，分别收口：

1. 工具契约补齐与任务场景边界整理。
2. 整个 Agent 对话工作区的阅读与操作布局重排。

子 Agent 并不否定，也不要求迁移框架；在这两个基础交付之后，单独做一个只读文档研究委派试点。先解决子 Agent 也会依赖的工具参数、资料能力与展示边界，不把三批工作叠成一次大改造。

## 2. 现有清楚的边界，应该保留

源码路径以仓库根目录为基准，Java 前缀为 `ai-collab-backend/src/main/java/com/shitulelv/aicollab/`。

- `agent/domain/tool/AgentTool` 有 name、definition、execute；具体业务 Tool 调用真实业务服务，是一次能力执行入口。
- `agent/domain/model/AgentSkill` 提供 instruction、outputContract、allowedTools 和场景元数据，没有 execute，不直接替业务服务完成动作。
- `AgentToolRegistry` 注册/暴露工具，`AgentToolCallExecutor` 校验和执行，Native 协议由 `NativeToolCallingExecutor` 发送定义，正式业务服务决定权限与业务条件。
- 模型决定本轮调用哪个可见 Tool、用哪些参数；普通 Tool 可以只查询数据库，不需要内部再调用模型。规划或子 Agent Tool 才会额外发起模型过程。
- 权限、审批、资源范围、版本、防重复、暂停准入和预算由程序保证，不能改为“提示模型自己遵守”。
- 工具暴露与执行时复核都需要存在；把一次校验删掉不等于低耦合。设计要使两者契约一致，同时允许执行阶段重新核对当前安全事实。

## 3. 本轮新核对的具体问题

### 3.1 部分 Tool 的模型输入契约不完整

`AgentTool.definition()` 默认返回泛化说明和 `openObject`。默认 Schema 只有 type=object、additionalProperties=true，没有 properties 或 required。

本轮检查了继承路径，以下生产工具没有覆盖成完整业务定义：

| 工具 | 执行代码实际上需要什么 | 模型可见定义的缺口 |
|---|---|---|
| `get_task` / TaskGetAgentTool | 必需 taskId，且必须为 UUID | 没有声明 taskId 属性与必填要求 |
| `search_project_knowledge` / KnowledgeSearchAgentTool | 必需 query；可选 documentIds、limit；执行端有各自边界 | 没有声明查询字段、来源过滤和数量范围 |
| `answer_project_question_with_sources` / ProjectQuestionAgentTool | 委托同一个知识检索工具 | 继承同样的泛化定义，名字也容易误导为另开问答模型 |
| `list_recent_audit_summaries` / AuditSummaryAgentTool | 可选 limit，默认 10，范围 1-20 | 参数和范围未进入模型 Schema |
| `draft_weekly_report` / WeeklyReportDraftAgentTool | 可选 days，默认 7，范围 1-30；实际返回统计 | 参数未明示，名字容易让人误以为 Tool 内部生成完整 AI 周报 |
| `update_task_after_approval` / UpdateTaskApprovalAgentTool | 目标 taskId、changes 和业务版本；需兼容可信提案修订 | 默认定义仅被 Registry 加入 approvalId，没有完整目标和修改字段说明 |
| `create_milestone_after_approval`、`update_milestone_after_approval` | 业务 DTO/目标 ID/版本校验 | 继承泛化定义，缺少对应参数契约 |

相比之下，任务列表、里程碑列表、成员、文档阅读、规划、任务创建提案、记忆创建和澄清已有显式定义。因此不是“所有工具都没有 Schema”，而是生产契约不一致。

这是源码确认的缺口，不是本轮实测到调用失败。模型可能从名称、提示词或失败反馈猜对参数，历史成功也不能证明定义完整。缺口会使模型和子 Agent 的调用依赖猜测，增加参数纠正与往返。

`AgentSkillToolMappingTest` 当前主要验证名称/写类型映射，许多对象使用 stub；测试注释虽然提到真实实现，并不能据此认定已检查全部生产 Tool 的 definition。下一轮应使用真实生产工具实例及工厂生成的工具，业务依赖可 mock，避免用手写同名 stub 证明真实 Schema 完整。

### 3.2 自动 Skill 路由和工具限制绑得过紧

`AgentSkillRegistry.select` 用显式 code、关键词、页面路径和兜底场景选择 Skill。Registry/Executor 再把 allowedTools 当作当前场景的硬限制。

例如“分析项目进度，并结合需求文档解释风险”：无显式 code 时，“项目进度”会命中 PROJECT_HEALTH；该 Skill 的工具集合没有知识检索或正文读取。这里不是模型判断资料不需要，而是模型尚未判断前，程序已经不给它这些工具。此例是源码路径推演，未调用真实模型复现。

自动路由依赖“任务”“创建”等宽泛词；页面路径又有单独硬编码，未从 recommendedRoutes 元数据生成。这适合快捷场景，但不适合当作所有综合问题的能力上限。

### 3.3 Skill 的输入 Schema 并非实际 Tool 参数

Skill 的 inputSchema 通过 AgentSkillResponse 返回给前端，但自由对话提交 DTO 是 content、skillCode、pageContext、pausedRunId。前端没有按这个 Schema 收集 focus/query/days 等结构化场景参数；调用链也没有按它验证自由对话输入。

因此不能把 Skill.inputSchema 解释成“当前请求已按此 Schema 执行”，更不能让它替代 Tool.definition().inputSchema。它目前更像场景表单元数据，不是现行对话执行契约。

处理建议：明确其兼容/元数据性质，不开发一套动态表单来使闲置字段突然变得必要；也不为清理字段破坏现有 API。前端场景列表保留 code/displayName/description 即可服务本轮设计，其他元数据暂保留并说明。

### 3.4 输出模板和用户目标的优先级需要更清楚

部分 Skill 输出结构较强，例如迭代规划要求迭代状态/目标/分配/风险，但该场景也服务单项任务创建/修订。Skill 不是模型的全部身份，用户只要一项事实时不应总凑满场景报告。

项目健康等已有“只读必要事实、没依据不补内容”的改善指令，应保留。下一轮让输出约定作为建议结构，明确用户本轮目标优先，不新增每次必走的固定流程。

### 3.5 预算与 Skill 的关系不是当前所见名称那么简单

Assembler 先按 run.skillCode 取得 limits，Coordinator 后选择实际 Skill；创建时普通 run 为 12 步/8 工具，显式迭代规划为 24/16。自动选中的 Skill 不等价于显式选择的预算。

这是既有设计差异，不在本批自动改成所有路径相同。下轮应补边界测试与说明，不因为减少关键词路由就顺带扩大额度、重算旧运行或改用量结算。若后续需要统一有效预算，应独立设计创建、续跑与恢复的兼容，而不是只改 forSkill 一行。

## 4. 目标边界：三层足够

| 层 | 应负责什么 | 不应负责什么 |
|---|---|---|
| Tool | 业务能力、清楚描述、参数 Schema、结果与覆盖语义、真实执行/校验 | 判断整段用户需求属于哪种场景、授予权限、套最终答案模板 |
| Skill/任务场景 | 专业指引、资料收集建议、建议工具和回答结构 | 代替 Tool 定义参数；用自动关键词把综合问题永久缩成窄能力；等同执行完成 |
| 运行策略/业务边界 | 身份、角色、项目、协议、根/子范围、写模式、审批、预算、恢复与执行准入 | 生成业务结论或凭模型输出变更权限 |

子 Agent 将来是带限定任务/上下文/工具范围的运行单元，复用这三层，不是把 Skill 类改名成 Agent。

这不要求新增三个“引擎”。可以在既有 Tool、Skill、Registry、Executor、Composer 中有限修改；只有真实共享逻辑才提取方法或小组件，不预设新接口层。

本轮还读取了本地课程 `lca-lc-foundations/notebooks/module-3/3.4_dynamic_tools.ipynb`：它按运行 context 中的可信身份过滤本次可见工具。可借鉴的是“任务提示与工具授权分别表达、每次请求提供清楚能力集合”，不是照搬教学 SQL 工具，也不是给当前项目增加 Python 中间件或另一次路由模型调用。

## 5. 下一轮交付 A：工具契约与场景能力边界

### A1. 完整声明实际生产工具

- 为生产内部 Tool 明确业务说明和参数 Schema；无参数工具也明确只接受空对象，不把泛化开放对象当正式契约。
- 优先补 get_task、知识检索及其别名、审计/周报统计、里程碑提案和任务更新提案；同时核对其余注册工具。
- 模型定义必须匹配当前合法参数、默认值、范围和返回语义；不要为了 Schema 整齐改变业务行为。
- 审批工具保留 approvalId 补丁及合并后完整验证。初次创建/更新的必填与可信 PENDING 提案部分修订是不同准入；补 required 时不能把合法补丁在合并前拒绝，尤其嵌套 changes.version 等字段。
- 复用现有 ToolArgumentValidator 及业务 DTO 校验，不引入通用 Schema 引擎、自动反射文档平台或新的业务写路径。
- 名字容易误导的工具先改模型说明与用户展示，不全量重命名持久 tool_name，避免破坏旧 invocation 恢复。

### A2. 跨场景基础只读能力，保留写能力控制

建议主 Agent 的有效内部工具集合为“共同基础只读集合 + 场景补充工具”，再由既有角色、协议、运行范围和写限制过滤。自动场景选择继续提供提示，不再因为命中健康/研究等场景就阻断必需的跨资料读取。

基础集合限定为：项目概况、任务列表/详情、里程碑列表、成员、文档目录/提纲/正文、知识检索及澄清。不是给模型所有工具，更不是开放 SQL、shell、任意 HTTP 或全部 MCP；外部工具继续按原 Skill/项目白名单与 Schema 确认策略。

显式只读场景、Legacy、非管理用户、scheduled/子运行等限制不放宽；写/规划能力仍遵守原场景写开关及真实运行策略，不将“取消关键词限制”理解成“自动授予写能力”。基础只读扩展先只作用于主运行，未来子 Agent 仍受自己的窄白名单。

暴露与执行复核使用相同有效工具规则，Executor 仍重新核对身份、范围、参数和暂停/claim；避免出现“模型看得到，执行阶段却因同一静态规则必定拒绝”的契约漂移。恢复旧 batch 不按新名字改写旧调用，不绕过当前权限。

### A3. 场景指令、轻量路由与兼容

- 前端展示“任务场景”，保留 skillCode/API/数据库标识和现有显式选择，不搞全量改名。
- 自动关键词只能作提示选择，不用宽泛词强制安排业务步骤；删除/收窄明显过泛规则应以相应样例验证。
- 输出结构按需求取舍；明确短问短答、综合问题按结论/依据/风险/建议组织，但不强制每条回复都出现所有栏目。
- 明确 Skill.inputSchema 是目前未执行的场景元数据，不与 Tool 参数混用，不开发动态表单。
- 不新增单独模型路由调用、不建设动态 Skill 安装器或插件平台、不改原审批/预算/恢复状态机。

### A4. 代码范围与验收

范围：`agent/infrastructure/tool` 的真实定义，`AgentToolRegistry`/`AgentToolCallExecutor` 的一致有效工具规则，必要的 `AgentSkillRegistry` 与场景指令/Composer，及现有相关测试。Recorder、业务写事务、租约、用量和模型快照原则上不改。

必须证明：

1. 真实生产工具定义包含所需参数；缺 taskId/query、越界 limit、未知字段等能在正确边界拒绝；合法参数不变。
2. “项目进度 + 文档依据”等综合只读问题在不同场景下能取得必要资料；简单任务查询不被迫生成整份报告。
3. 未授权、Legacy、显式只读和子范围不能获得写/规划能力；未知工具不能执行，MCP 原控制不变。
4. 提案新建、可信部分修订、版本冲突、重复调用，以及旧调用恢复均不回归。
5. 现有暂停/输入续跑、自动重试、已保存结果恢复和下一请求配置切换仍成立。

最小质量对照用现有方式做 3-5 个有事实基准的问题：跨资料进度分析、任务详情、文档检索/证据不足、单项提案及修订。定向测试是结构保证；真实模型结果单独记录，不把历史测试数或一次猜对参数当作完成证明。

## 6. 下一轮交付 B：整个对话工作区重排

用户已确认范围：正文、过程活动、两侧栏；不是只给文字加粗，也不是重做全站。

- 中央长回答作为阅读正文，取消助手长文的窄气泡约束，稳定可读行宽；用户问题保持紧凑区分。
- 标题分级、重点、列表、表格、引用与代码建立层级；优先既有 marked + DOMPurify，不加二次模型“美化”调用，不正则猜重点。
- 真实过程紧凑且可折叠；最终答案、来源和待处理动作优先，工具原名/错误诊断放详情。
- 会话栏可收起；右侧优先审批和规划，参考模板及底层连接诊断不占主要阅读位置；输入区和控制状态稳定。
- 场景选择作为可选任务偏好，不能让用户误以为没有选 Skill 就没有 Tool；保留现有 code 和接口。
- 移动端优先对话/输入，侧栏按需打开；不新增继续按钮，已受理规划继续完成。

范围：AgentView、必要的对话/活动/侧栏子组件、相关布局与 Markdown 样式、轻量输出约定和相应测试。状态由现有 workspace/timeline 投影，不再建第二套前端运行状态。

验收：用 browser-skill/bsk 采集当前页面并在桌面/窄屏检查短答、长报告、表格、流式预览、工具活动、失败/自动重试、暂停、审批和来源原文。不能凭截图漂亮代替回答质量，不要求所有提供商新增逐字流式。

可在该批定向复现 FAILED_RETRYABLE 刷新恢复；如证明确有影响，仅补前端恢复入口与测试。这不是重新审查已收口 SSE sender。Legacy 输入转换缺口可在交付 A 参数捕获测试中核实，明确局部问题后独立修补，不借机迁移执行器。

## 7. 子 Agent 后续批次

下一轮不同时交付完整多 Agent 系统。保留一个只读 document_research 试点作为紧随其后的批次：主 Agent 可通过委派 Tool 把多次检索/正文对照交给子 Agent，拿回发现、来源和覆盖缺口。

复用现有持久运行引擎，最多一层，不让每个普通查询多走一次模型；不使用新的编排框架，不直接开启遗留 delegation 分支。接入前定清父等待/子完成唤醒、共享预算、控制输入与暂停、结果身份、避免主会话污染以及子范围只读权限。既有父子字段只能作为可审查基础，不能当作完成证据。

质量收益按同一组多文档任务对比单 Agent；如没有明显更完整/可靠的回答，不继续扩角色和并行平台。调用原理简单，集成工作也应限定在这些现有边界，不把工程可靠性解释成必须开发通用多 Agent 产品。

## 8. 开发停止条件与不做项

交付 A 在工具真实契约完整、综合只读资料可获得、安全与恢复契约回归通过后结束；交付 B 在工作区阅读清楚、控制行为保留、桌面/窄屏验收完成后结束。可以拆成两个独立提交/验收批，不互相拖成长期重构。

本批不做：Skill/数据库/API 全量改名、LangChain4j/LangGraph/Spring AI 迁移、第二套循环或 checkpoint、动态插件平台、自动择模、精确费用体系、继续按钮、所有 provider 流式扩展、全站 UI 改版、跨终态剩余工作续接。

本轮结论依据生产源码与已有材料，未运行新测试或模型；具体改动仍须在下一轮开发中验证。此前 Git 工作区内容保留，不修改或收编无关 `.freebuff/` 与继承审查证据。
