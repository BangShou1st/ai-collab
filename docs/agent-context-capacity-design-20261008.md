## 1. 先确定要改变什么

用户希望大文档研究不再因默认 50k 输入额度过早结束，并借鉴长上下文 Agent 在窗口接近满时压缩、继续工作的方式。

**决定：活跃上下文逐步增长，到约 256k 时压缩可压缩的旧轨迹，再继续增长。256k 既不是整轮累计输入额度，也不是模型每次只能接收的硬上限。** 本文的 k 按 1000 计，即 256000 tokens。

Codex 的官方配置把 `model_context_window` 与 `model_auto_compact_token_limit` 分开；压缩阈值未设置时使用模型默认值。可以借鉴这种区分，但不能把“所有 Codex 都固定在 350k 压缩”当作已核实的统一规则。[官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

当前至少有五个不同限制，不能只改一个数字：

| 层次 | 仓库当前实现 | 需要改变的方向 |
| --- | --- | --- |
| 单次输入 | `AgentContextProperties` 默认 50000 | 按模型实际容量与输出/安全预留判定硬边界，移除已确认大模型上的额外 50k/256k 硬限 |
| 整轮累计输入 | 常规根运行数据库默认 50000，运行时也有 40k/50k 限额 | 新策略取消硬限，只统计实际/估算用量，不用于收尾、受理或拒绝新请求 |
| 资料读入 | 正文工具默认 3000、最大 6000 **字符** | 有界扩大正文页，保留准确的续读与版本契约 |
| 资料保留 | 工具层最多 24000 字符；最新结果 6000、旧结果 1500 字符投影 | 有空间时保留必要原文，不因变旧自动截成小摘要 |
| 摘要 | 每运行至多一次；6000 字符输入、1200 字符输出，只处理旧会话片段 | 增加同一运行内研究轨迹的窗口压缩，复用现有摘要准入与持久化 |

这些是源码默认值，不是本轮读取正在运行的进程环境/生产数据库后确认的有效配置。现有代码没有自动识别每个模型的真实窗口；“当前所有模型都是 1M”也没有在本轮逐型号核实。

## 2. 模型硬边界与软压缩触发分开

每次新模型请求，基于同一请求配置快照解析：

```text
W = 本次模型配置的已确认上下文容量
R = 本次实际发送的最大输出额度（包含适配器定义的思考/输出语义）
S = token 估算与消息封装的安全余量

H = W - R - S                  # 模型安全可用输入，真正的单次硬边界
T = min(256000, floor(H * 0.85)) # 软压缩触发线；小窗口提前触发
L = floor(T * 0.50)            # 压缩后总活跃上下文的软目标
```

- 已确认的 1M 模型且输出预留允许时，T 为 256k，压缩目标约 128k；H 仍接近模型实际容量，而不是 256k。85%/50% 是第一版候选策略比例，不是提供商协议。
- 一个工具批次让活跃上下文从 250k 跳到 275k：这是触发压缩，不是协议违规或 BUDGET_EXCEEDED。只要 H 内仍有空间，就能完整读取可压缩来源并进行摘要。
- 若当前必要原文/状态本身超过 T，或者摘要失败但原请求仍在 H 内，不得仅因超过 256k 而拒绝、截掉必要证据或反复压缩；可以有界继续。L 也不是达不到就判失败的硬约束。
- 较小窗口模型自动得到较小 H/T；不把 128k 模型强行按 256k 发送。接近 H 时才必须确保本次请求与输出可安全容纳，否则缩小取证范围/有依据压缩/部分交付。
- 优先复用现有 `window-overrides`，并把解析后的窗口事实带入 `ResolvedRequest`；第一版不建设自动模型目录同步平台，不因本需求扩建 AI 设置界面。
- 模型容量未知时保留现有 50k 兼容回退，并明确 `estimated/unknown`。这不是对任意未知小模型的安全保证；启用新的大窗口策略前必须核实并配置当前型号/端点的容量。
- 工具 schema、系统提示、角色消息封装、子产出和尾部指令都计入输入，不只计算正文。预算必须在最终出站消息上再核对一次。
- 不能仅沿用 `chars/3` 再把 cap 放大：中文、代码和 JSON 的误差需要独立测试。支持匹配 tokenizer 时使用它；其他情况采用保守估算并标记来源，估算路径以至少 10% 余量作为校准起点。不能把这个比例当成准确性证明或精确计费。
- 256k 是整理旧轨迹的策略线，不是必须填满的目标。短问题仍应短请求、直接完成；不能为“利用大窗口”加载全项目。
- 触发统计的是当前实际活跃上下文 C，不是累计 `input_tokens_actual`，也不是历史所有工具结果的库内大小。C 包含有效摘要、尚未压缩的相关轨迹、近期原文、必要状态与工具定义；应在固定投影/淘汰旧材料之前判断压力，不能先截掉来源后宣称尚未达到压缩线。

## 3. 输入输出只统计，执行仍有边界

**新策略不设累计输入或累计输出 token 上限。** 不采用 8M 输入、128k 根输出或 32k 子输出，也不换成另一组更大的累计数字；同时保留现有用量记录、同调用一次性结算和父子回收，不删除可靠性基础。提供商可能另有账号额度/速率限制，它们不是本应用的整轮累计 token 上限。

压缩解决的是当前上下文容量，不会减少已经发生的请求消耗，也不能单独防止无限执行。每个运行自己的有限决策轮次、工具/推进额度、depth/子数量、活跃时长、重试次数和循环检测负责防失控。无需再以累计 token 重复限制正常研究。

建议新运行采用以下统一资源保护起点，不继续给每个 Skill 堆叠一组 40k/50k 上下文策略：

| 新运行保护 | 根运行建议 | document_research 子运行建议 |
| --- | --- | --- |
| 活跃上下文 | 256k 软压缩触发，模型容量为硬边界 | 同一规则，按自身角色选择内容 |
| 累计输入 | 不限额，只记录真实/估算消耗 | 同样不限额，实际用量按现有身份回收一次 |
| 累计输出 | 不限额，只记录真实/估算消耗 | 同样不限额 |
| 单次最大输出 | 当前请求配置、模型能力与本次窗口共同约束 | 自己的请求使用同一规则，不从父剩余输出切分 |
| 推进步 | 自身最多 64，不追加子步骤用于额度判断 | 自身最多 16，独立于父剩余步骤 |
| 自身决策模型轮 | 24 | 12 |
| 工具总调用 | 自身最多 64，委派本身计 1 次 | 自身最多 24，不从父剩余工具数切分 |
| 单轮工具 | 保持 4 | 保持 4 |
| 子运行数量/深度 | 保持最多 3 个、仅 depth=1 | 不再创建下一层子运行 |
| 活跃执行时长 | 自身建议 45 分钟 | 自身建议 30 分钟，不继承父剩余时长 |
| 研究窗口压缩 | 最多 4 个有效触发周期 | 最多 4 个有效触发周期，不碰主会话摘要 |
| 可恢复模型失败自动重试 | 保持最多安排 2 次的现有规则 | 同一引擎、同一规则，不无限重试 |

说明：

1. 这些是上限，不是模型必须用完的计划。达到用户目标就结束，不额外调用模型判定“问题复杂度”。真实质量验收可以下调或上调，但须说明依据。
2. 重复发送、摘要请求和子运行等仍累计记账；累计输入超过旧 50k、旧子 30k 或已撤回的 8M 建议值，都不单独触发新策略的收尾/失败/拒绝。不能把 24/64 等执行保护候选直接认定为真实任务已验证的合理额度。
3. 累计输入和累计输出均退出准入、收敛、委派切分与失败判定；提供商单次输出参数继续有效。原始 usage 缺失时继续如实标为估算/未知，不建设精确价格产品。
4. 当前数据库的 max_input_tokens/max_output_tokens 都是运行累计上限，不能与模型配置的单次最大输出混用。取消累计限额必须兼容迁移：v2 两者用 NULL 明确表达“无累计限额”，保留非负计数；v1 保留原值/约束语义。不用 0、8M、Integer.MAX_VALUE 或一组假额度冒充“关闭限制”。详见第 8 节。
5. 消除新策略下 Repository 创建、`AgentRuntimeLimits`、Coordinator 和失败重试之间的隐藏 `min` 冲突。Coordinator 的两个 300000ms 上限与 Recorder 失败处理的 300000ms 判断也必须读取同一有效策略，不能改了 45 分钟后仍在 5 分钟被另一层判停。
6. 时长是各运行的活跃执行计量，不把排队/暂停/离线算进去，也不能把根运行 45 分钟宣称成整棵委派树的墙钟承诺。继续使用现有持久计时与 deadline，不新增第二套任务调度器。
7. 规划、审批、写动作的权限/版本/串行化不随容量放宽；已受理的后台规划仍独立完成。

额度作用域与到限行为必须说清楚：

- v1 保留现有共享额度/回收语义；v2 根和子分别限制自己的步骤/工具调用，子 16 步/24 工具是独立上限。父只承担委派自身 1 次工具及自己的综合执行，不能回收子用量后把父自身执行额度扣光。用量仍真实统计并只回收一次；子消耗的统计不是父执行额度的扣减。父步骤/工具诊断须明确标为自身，不把它与全树消耗混用。
- 自身决策模型轮按各运行的 MODEL_TURN 计数，包含其最终综合轮；不把子轮次伪造为父自己的模型轮。摘要调用另以持久压缩周期限制，每次辅助出站也记录身份/用量。
- 新 SEPARATED 的推进仍为模型轮 + 回答落库；工具结果只计工具次数。COMBINED 旧运行不重解释。四个同轮工具仍计四次工具额度。
- 单轮最多提出 4 个工具，不等于 4 个同时执行：现有 Scheduler 每 run 桶并发 2、用户桶并发 4，共享池 16/队列 64，第一版保留，不新增线程池。无进展循环检测保留；验收正常分页和压缩后有依据的原文回读，不把它们简单当作重复循环。
- 当前内置工具 10 秒、MCP 15 秒的默认超时不属于 token 额度。本轮用户要求进一步放宽超时，建议新策略内置工具默认 30 秒、MCP 120 秒，并按真实工具性质校准；模型单次请求建议 10 分钟、连接 15 秒。实际调用还受本运行剩余执行 deadline 限制，不能继承父剩余 deadline。正文页扩大时一起校准结果字节保护，不能把超时误报为资料不足。
- 单次最大输出取用户当前配置，并按模型协议与本次实际窗口调整；不与累计已生成 token 相减。主决策、摘要、兜底请求都遵守本次最大输出限制，不能借取消累计限制突破单次上限。输出 token 与思考 token 的关系按适配器/提供商语义处理，不假定各家相同。
- 256k 或压缩后目标触及不会单独判失败。压缩周期满则不再新增无界摘要请求；只要必要输入仍在 H 内，可继续原上下文。真正的轮次/工具/时长到限，应提前收尾并保留已经取得的有限证据/文字/引用；不能丢保存结果或把部分交付伪装成完整研究。单次输出截断不是累计额度耗尽，不自动等同整轮任务终态；保存部分文本与停止原因，按既有有界流程处理，不执行不完整的工具参数。
- 本文没有承诺“除这些以外所有程序字段都无限制”：单页字符/字节、schema 参数、分页、并发、HTTP/上传等仍有各自安全边界。它们不等于累计输入额度，不因本次扩容统一撤销。

v2 的累计输入/输出不参与模型安全输入 H、压缩触发 T、摘要请求准入、收敛、Worker 预检查、兜底模型请求或委派受理。模型决策轮和摘要调用分别核对自己的 H/单次输出预留；不计算“累计 token 剩余的一半”，也不按上轮输入的两倍提前结束。已有用量事实继续持久化，不因压缩清零。

这不是只删除一个条件：必须一起复核 `AgentWorker` token 到限检查、`AgentContextBudget` 的 remainingRunInput 绑定、`AgentConvergencePolicy` 的累计输入/输出收尾、Coordinator 主请求/摘要/兜底准入与响应用量处理，以及 `AgentDelegationAdmission` 和 Recorder 的子额度切分/父回收扣减。v1 兼容分支继续原语义，v2 的入口共用同一策略事实，不能漏掉一处让旧 50k/30k 输入或 20k/8k 输出限制暗中生效。

### 3.1 当前计时机制与下一轮修订

本轮源码复核的当前行为（不是生产运行实测）：

- `AgentRepository.claimNext` 领取时写 claim_started_at；`activeElapsedMillis` 为已落库的 active_elapsed_ms 加当前 claim 至今的时间。Recorder 退出 claim 时结算并清空开始时间。
- claim 内等待模型 HTTP 和工具结果也算活跃时间，不是 CPU 计时。正常排队、暂停、重试间隔、父等待子运行期间不持续计时；父重新领取后检查等待子状态的短时间会计入自身。
- 崩溃接管只累计到上次已确认进度，不把服务离线到租约过期的等待算成已执行。
- 默认研究的 maxRunDuration 为 3 分钟，部分 Skill 为 2--5 分钟；Coordinator 还有 min(300000, skillDuration) 的硬封顶，Recorder 判断是否还可自动重试也有 300000ms 判断。
- 每次推进的剩余时长传入 AiRequestDeadline；实际模型请求超时取提供商传输超时与运行剩余时长的较小值。工具另有自身超时；运行到限检查/请求 deadline 不是任意业务写事务的强制中断开关。

用户已认可累计 token 仅统计与父子独立执行的方向，并要求超时再放宽。下一轮建议保留单次模型/工具超时，把运行活跃时长统一为可配置兜底保护（候选根 45 分钟、子 30 分钟，不是业务完成 SLA）；模型单次请求默认 10 分钟、连接 15 秒，内置工具默认 30 秒、MCP 120 秒，允许依据工具性质/提供商能力配置。参数是第一版待验收值，不是声称已适合所有模型。

各运行单独计时，父不累计子耗时，不把父 deadline 传给子请求；父暂停/取消与子回收行为仍按既有可靠性规则处理。正常完成不等待计时器，到限禁止继续扩展研究并保存已有成果，不能无限追加收尾调用。核对实际 Agent 的 JsonHttpModelClient 出站路径，不能只修改 Spring AI 聊天配置后宣称 Agent 已放宽；尽量避免影响无关聊天/规划调用。

**长请求必须配套核对租约。** 当前 AgentRuntimeJob 每次 claim 的租约固定 6 分钟，AgentLeaseScope 会校验过期与 claim epoch；模型 HTTP 默认超时为 3 分钟。单次请求放宽到 10 分钟后，不能留着 6 分钟租约等待它自然过期，也不能简单把租约延长到 45 分钟导致崩溃接管明显退化。复用现有 worker/恢复/租约机制，选择最小的有界续租方案：只有仍持有当前 claim 的活跃 worker 可续租，失去租约/取消/到限/退出时停止，保持 epoch fencing、不跨 HTTP 持数据库事务锁、不建设第二套编排。用受控时钟和阻塞模型验证长请求成功提交、旧 worker 被接管后不能写入、崩溃后仍按既有短租约窗口可恢复；测试不需要真实等待 45 分钟。

## 4. 原文优先的上下文选择

复用 Composer，统一正常、降级重组、无工具综合和预算兜底所需的证据层，避免在 Coordinator 分支末尾临时追加后又在重组时遗漏。

### 4.1 不可被摘要替代的内容

- 系统安全/角色规则、当前用户目标、有效用户更正及原话来源。
- 与本动作有关的可信业务状态/审批版本；旧摘要不能替代当前数据库授权。
- 当前未消费的模型响应、尚未完成的工具调用，以及 Native/Legacy 所需的协议身份。
- 已回收子运行的必要结论、引用和准确的 coverage；UNTRUSTED 文字与后端提取的覆盖事实分层，所有组装分支保留。
- 引用对应的 document/snapshot/chunk/range 身份与实际覆盖限制。研究总结不自动获得“已校验事实”地位。

“保留”不代表无限复制：去重、紧凑字段和有依据的范围表达仍可做；无法放入必要层时明确反馈，不能悄悄去掉用户更正或子证据后继续成功。

### 4.2 有空间时完整保留

- 近期相关对话与当前研究已读取的正文/工具结果，优先保留必要原文；C 达到 T 时整理可压缩旧前缀，不因超过 T 就截断最新资料。
- 移除工具观察 24000 字符总顶，以及“变成旧结果就最多 1500 字符”的固定压缩规则。Projector 继续作为有压力时的确定性投影组件，不用作正常情况下强制丢正文的入口。
- `HISTORY_CANDIDATES=40` 只是查询候选，不应成为“明明窗口有空间却只能看 40 条”的逻辑丢弃边界。按有界分页加载相关活跃来源，达到触发线后压缩已有前缀，再继续必要加载；不能一次加载无限历史，也不能在 T 处无标记截掉尚未被摘要覆盖的来源。已有效压缩的前缀不重复加载。
- 过滤无关项目记忆、重复调用结果、已失效目标；不新增模型相关性分类器。
- Native 工具调用与结果必须作为完整协议块选择/压缩，不留下孤立 result、遗漏同轮调用结果或虚构新 toolCallId。同批多调用应保留闭合批次契约。

子研究只选 objective、必要项目身份、允许的研究观察与自身摘要；不继承主对话目标、提案修订规则和追问模板。`composer-v2=false` 的兼容组装也遵守这一角色隔离，不把它误认为 Legacy 模型协议。

## 5. 窗口压缩的实际含义

### 5.1 压缩的是旧研究轨迹，不是删除资料

当活跃候选上下文估算达到 T，选择最旧的、已经闭合且可压缩的对话/工具块；没有可压缩旧前缀时不重复发起摘要，不把阈值当拒绝受理理由：

```text
旧有效摘要 + 本次确实提供的旧轨迹
    -> 一次不带业务工具的摘要模型请求
    -> 可用于后续研究的摘要 + 后端记录的真实来源范围
    -> 摘要 + 近期原文 + 必要证据/状态，重新组装当前请求
```

- 不尝试把 256k 材料塞进现有 6000 字符摘要输入，然后声称全窗口覆盖。摘要请求本身也按模型窗口计算容量；一次不能覆盖的前缀明确保留未覆盖范围。
- 摘要正文的建议输出目标为 4k--8k tokens，内容包括已确认发现、决定、更正、未完成问题、来源定位和缺口；不要机械限制到 1200 字符。
- 大窗口模型的 L 约 128k 是压缩后**所有活跃内容合计**软目标，不是要求摘要长达 128k，也不是强行把刚读到的关键原文压缩掉。必要原文使合计超过 L 时允许保留。
- 原消息、原工具结果和引用仍在 PostgreSQL；摘要是模型可见视图，不能改写工具成功次数、真实来源或正文覆盖。
- 摘要可能遗漏或误述。需要精确条件、数字、措辞时保留/重新读取原文。不能承诺无损压缩，也不能把摘要当全文证据。

### 5.2 复用现有持久化，不加第二套记忆平台

继续由 `AgentContextSummarizer` 承担摘要请求、质量检查与结果提交；复用 Recorder 的摘要准入、调用身份、结算和短事务。

- 主会话历史摘要仍使用现有 `working_state.summary` 与消息/偏移覆盖，保留其已有兼容数据。
- 新的**运行研究轨迹摘要**放在已有 `agent_step` 的摘要记录 `output_json`，加入 `scope=RUN_CONTEXT`、schema/policy version、runId、目标修订、源 step/message 范围、来源摘要/hash、有效文本与引用身份。
- 两个 scope 共用生成/校验/记账规则，不建立两套执行循环。子运行只生成自己的 RUN_CONTEXT，不触发/改写主会话 summary。
- 来源覆盖由实际送入摘要请求的记录计算，模型不能填写“这些步骤全读过”；分页/partial 偏移必须准确。
- 每个 `scope + 源边界 + 目标修订/摘要版本` 至多一个有效压缩周期；先落尝试身份再出站，成功提交才推进覆盖。一个运行最多 4 个研究窗口周期，拒绝无新增来源的重复压缩。已有一次有界输出重压缩能力保留，并计入同一周期的调用/用量保护。
- 恢复时读取持久摘要与未覆盖记录，不因 JVM 重启重新压缩同一源区间；发生目标更正、CAS 冲突、失去租约时不得提交为当前有效摘要。

提交成功后要重新读取状态并**重新组装本次主请求**，不能继续发送摘要生成前已经组好的旧 messages。摘要请求和后续主请求各有自己的配置快照；后续主请求重新读取当前模型，窗口变小时重新适配。

### 5.3 失败与暂停

- 摘要失败/不合格：保留旧有效摘要与原数据，不推进覆盖。只要仍在 H 内可以继续原上下文；超过 H 时使用已有有界投影/证据交付，明确不足，不无界循环请求摘要。
- 必要原文无法保留：显式说明范围缺口，不假装研究已经完整，不直接清空全部历史。
- 暂停意图先落库：不启动新的摘要或主请求。已受理摘要允许完成并保存，但不能借此自动解除暂停。
- 取消、失败、额度终点：已经返回的合理正文/研究产出保存为部分交付，不再执行其中新工具调用。终态可仍为 BUDGET_EXCEEDED，不用 SUCCEEDED 粉饰完整性。
- 已保存未消费的模型/工具结果继续先恢复，再考虑新请求或压缩；不能让新策略拦截旧成果的消费。

## 6. 文档读入必须配套改善

仅放宽上下文而仍以 3000 字符一页取证，会继续被工具次数/耗时拖住。建议第一版正文页默认 12000、最多 24000 **字符**，而不是 24000 tokens。

- 同步修改 `DocumentContentService`、`DocumentAgentTools` 的 schema/default/range 和契约测试，不出现模型可见范围与执行要求漂移。
- 不新增全文下载工具；保留原有 heading/chunk/offset/snapshot 续读，以及每页有界读取。
- 中文页的 UTF-8 序列化可能超过既有 32kB 配置；相关结果大小保护/HTTP 序列化/事件投影需一起核对并有界适配，例如 128kB 级上限，不能只改 maxChars 后在另一层被拒。
- 文档工具返回的正文是 UNTRUSTED source data；窗口放大不使文档内容变成系统指令。
- 读取更多片段不自动证明整章/全文完整：后端覆盖继续核对版本、chunk 范围和偏移，不能把 `items.size()` 当章节数。
- 引用只有模型实际可见的材料才可支持具体结论；取到数据库但被投影/摘要遗漏的内容不能冒充模型读过。准确引用需要时通过原工具回读。

## 7. 委派配套：有空间，但不强制使用

主模型仍选择直接取证或 `delegate_document_research`。不新增“某关键词必委派”的硬路由，不以子调用率为成功指标。

- 受理仍使用 `AgentDelegationAdmission`；v1 保留现有切分，v2 从统一策略解析子自己的步骤/工具/时长上限，不从父剩余切出，也不把父请求 deadline 继承给子。委派自身仍占父 1 次工具调用，父须有能力发起委派并完成自身综合收尾；这一检查不能变成“父还剩几次工具，子只能读几页”。
- v2 不切分累计输入或输出额度，不给子运行另设 30k/4M 输入或 8k/32k 输出累计硬限，也不因父累计 token 增加而隐藏/拒绝委派。子运行按自己的模型请求 H/T 和单次输出配置管理请求，真实消耗仍回收到父统计一次，不用于扣减父自身步骤/工具额度。
- 暴露委派工具时计入即将发生的已知模型推进成本，并使用持久化 COMBINED/SEPARATED 语义；执行时照常复核。可预期受理拒绝保持真实 REJECTED 回执与有界继续。
- 子任务资料不足时返回已知发现/缺口，不能进入主界面无法回答的子 WAITING_FOR_USER_INPUT。真正需要问用户，由父综合决定提出。
- 只有一层，保持原白名单、禁止子业务写、同 invocation 幂等、不写主会话消息、父暂停不被回收唤醒。
- 宽松容量也不保证全库任务必完整；模型是否正确续读和引用仍需质量验收。

当前切分原本用于保证委派不放大整棵树资源，这不是模型协议要求。代价是父先研究再委派时子可用空间更小，子完成还可能耗尽父综合空间。v2 改为每个运行独立的有限执行、最多 3 个子且仅 1 层、现有并发保护；不额外建全树预算平台。例如候选父 64 次工具、3 个子各 24 次时，全树工具调用最多 136 次（委派自身已包含在父 64 内），不是无限运行。固定验收要同时记录任务质量和全树实际消耗，不能把此数学上界当成已验证的最优配置。

## 8. 旧运行兼容与单次请求快照

**资源策略版本与推进计数语义是不同维度。** 不能把现有 SEPARATED 解释为“已经用上 256k 软触发/新压缩”，也不能重新计算旧 COMBINED 步数。

建议用一个最小兼容标记 `agent_run.context_policy_version`：既有行默认 1；新根运行与终态派生重试写 2；子运行继承父版本。这个标记只选择已定义的兼容策略，不是可编辑规则引擎。

- v1 保持既有运行额度/上下文行为，恢复与暂停续跑不重解释；本轮可靠性缺陷修复可同时覆盖两条路径。
- v2 使用本文的模型硬窗口、软压缩触发、累计输入/输出仅统计、独立父子执行额度，以及运行轨迹摘要。仍有限额的 max_* 字段继续落库，不靠恢复时猜测“原来用的是多少”。
- 不批量更新旧运行。不改变旧摘要含义；老记录没有 RUN_CONTEXT 或 coverage 时按未知兼容。
- 模型/窗口事实不是整轮固定值：每次请求从当前配置解析快照，组装、能力、工具暴露、输出封顶、出站、响应校验用同一份；下一请求重新解析。
- 为本次请求派生较小最大输出时，仅生成内存中的有效请求参数，不能改数据库用户设置；Native/Legacy/提供商预置适配要实际收到同一派生值。

这需要一项明确迁移：兼容标记和 max_input_tokens/max_output_tokens 可空/计数约束。不要堆多个 profile 表、预算账本或新 checkpoint 表。

- 既有行/v1 的 max_input_tokens/max_output_tokens 保持原值；新根运行、新派生重试与其子运行的 v2 两者明确写 NULL。约束区分旧限额行与新无限额行，其余步数/工具/非负用量/版本等约束不删除。模型配置的单次最大输出不设为 NULL，仍保持有效值。
- `AgentRunView`、JDBC mapper、执行限制/受理事实和前端类型必须正确表达可空上限；不能把 JDBC NULL 读成 0，也不能对 NULL 做旧的 min/比较/对半分配。
- token 计数与 actual usage 保持一次性结算；v2 输入/输出不按旧 max 封顶，不把封顶预算计数冒充实际消耗。v2 步骤/工具 used 只计当前运行自己的推进/调用，子实际步骤/工具可从已有回收记录与子步骤查看，不再添加到父的执行 used。旧恢复/回收保留其原 budget-used 与 actual 区分。
- 前端只做契约所需的小改动：无累计 token 上限时展示实际用量/估算来源，不展示输入或输出“剩余额度”或百分比；父步骤/工具标明自身计数，不把全树消耗与父自身额度比较。不是对话工作区重设计，不重开 SSE。

## 9. 同轮必须修的成果保真问题

容量放大不能掩盖 [全面审查](E:/project/ai-collab/docs/agent-comprehensive-review-20261008.md) 的真实反例。以下属于同一研究链的正确性要求：

| 审查项 | 开发终点 |
| --- | --- |
| F1：子追问导致父持续等子 | 子产出部分发现/缺口并回收，父可交付；子提示词不继承父追问规则 |
| F2：降级重组丢子成果 | 正常、缩减、最终综合都从统一必要证据层组装 |
| F8：输出超额后丢已返回正文 | v1 累计超额仍保存部分产出；v2 不因累计超额判死，单次截断/异常返回也保存文本/引用/实际 usage，不执行不完整或未准入的新工具 |
| F3/F4：覆盖数量/分页/版本错误 | 区分片段与完整章节，去重范围、闭合续读；跨快照不合并为已校验版本 |
| F5：子继承提案/主会话 | 两条组装路径按角色一致隔离，不用提示词“忽略上文”代替数据选择 |
| F6：必然拒绝的委派仍可见 | 对齐已知推进成本与持久预算语义，不预测未知模型 token |

F7 的前端字面 `[QUESTIONS]` 误解析另作小范围补修；它与 256k 不构成依赖，不重新设计工作区或重开 SSE。本轮容量设计不把额外 UI 优化升级为必修。

## 10. 实现职责与开发顺序

| 入口 | 职责边界 |
| --- | --- |
| `AgentContextProperties` / `AgentContextBudget` / `ResolvedRequest` | 当前模型硬窗口、软压缩触发/目标与最终请求体积；不读业务表或决定授权 |
| `AgentRuntimeLimits` / Run 创建 / Convergence | 新旧资源策略解析、v2 累计输入/输出仅统计、每个运行独立的有限执行与收尾；所有消费者用同一有效规则 |
| `AgentModelMessageComposer` / Projector | 角色选择、必要层、原文保留、闭合协议块、压力投影；不发模型请求、不建子运行 |
| `AgentContextSummarizer` | 选择可压缩已闭合来源、无工具摘要、质量校验；复用 existing scope/持久请求边界 |
| Repository / Recorder | policy version、摘要源边界/有效提交、幂等结算、部分产出回收；锁不跨模型请求 |
| Coordinator / Worker | 消费保存结果优先、触发压缩与重新组装、准入下一请求；不维护第二份历史状态机 |
| `DocumentContentService` / `DocumentAgentTools` | 有界扩大正文页、schema 与执行一致、准确快照/范围/citations |
| `AgentDelegationAdmission` / Coverage | v1 兼容切分、v2 独立子执行额度与父自身发起/收尾检查、受理时点一致、实际来源范围事实；不由模型填写统计 |

建议下一轮一次完成以同一后端研究链为主的交付，包含累计输入/输出上限可空所需的最小前端契约适配；内部按三步实施和提交，不能只交“参数已调大”：

1. **容量与成果保真**：兼容迁移、统一资源保护、模型适配窗口、正文页与原文保留；把相关 F1--F6/F8 反例转正式回归并修复。
2. **真正的窗口压缩**：扩展现有 Summarizer 的 RUN_CONTEXT scope、多周期持久覆盖和重组；补失败/暂停/恢复/模型换小窗口测试。
3. **质量验收与文档收口**：固定资料直接/委派研究对照，分别报告覆盖、引用、缺口、模型请求数/耗时；维护入口只索引最终设计/实际交付，不复制第二份长规则。

不引入框架迁移、自动择模、问题复杂度分类模型、预算管理平台、第二套 Agent 编排或新的子 Agent 类型。授权实施时提交代码与文档/证据，保留无关未跟踪内容，不 reset、不 push。

## 11. 验收终点

### 11.1 自动化必测

- 已确认 1M 模型的压缩触发为 256k，硬输入不被另一个 256k cap 绑定；小窗口提前触发；未知型号回退明确；输出预留使用实际出站值。
- 250k 加一批工具结果变为 275k：触发摘要但不误报预算耗尽；无可压缩旧前缀/摘要失败、必要内容仍在模型 H 内时，可以继续并保留必要内容。
- v2 的累计输入越过旧 50k/子 30k，以及已撤回的 8M 数学边界时，不因输入累计单独拒绝新请求/摘要/兜底/委派；用受控用量 fixture 验证，无需实际消耗 8M。v1 仍按原额度恢复。
- v2 的累计输出越过旧根 20k、子 8k，以及已撤回的根 128k/子 32k 建议值时，不因此单独触发收尾/失败/拒绝；单次最大输出仍真正传给各适配器，窗口输出预留与出站配置一致。
- 数据库 max_input_tokens/max_output_tokens 的 NULL、JDBC mapper、后端视图/受理事实和前端类型一致；token 计数不按假上限封顶，父子结算仍一次，压缩不清零累计 usage。
- 父已用大部分工具/步骤但仍能发起委派并综合时，子取得独立额度；子完成不耗尽父自身执行 used。重复回收、父暂停/取消/竞争窗口及旧 v1 共享计数都回归。
- 各运行的活跃时长与单次超时分别生效；子不继承父剩余 deadline，等待子/排队/暂停/离线不冒充父执行时间。调整统一时长后不能被隐蔽的 300000ms 条件截停。
- 模型长请求超过原 6 分钟 claim 边界仍可合法保存，退出后停止续租，崩溃后可在短租约窗口接管；失去 epoch 的旧 worker 不能落库。流式/非流式及暂停/取消路径不泄漏续租任务或占用。
- C、本次 usage 与累计消耗分别统计；模型真实窗口、各运行决策轮/工具/时长/循环检测及单次输出保护仍有效，不能以“无累计 token 上限”为由无限执行或突破单次窗口。
- 有空间时旧正文完整进入实际模型消息；6000/1500/24000 字符旧常量不再暗中压住新策略。
- 至少两次研究窗口压缩可推进，已摘要源不重复塞入/重复结算；无源增长不反复压缩。
- Native 闭合多工具批次、Legacy 只读兼容，工具调用/result 身份恢复完整；候选加载不丢未摘要前缀。
- 摘要提交后当前主请求实际使用新摘要；旧目标/CAS 冲突结果不成为当前摘要；子摘要不修改主会话。
- 暂停前/在途/恢复、取消、摘要失败、输出超额部分结果保存、换小窗口、旧 v1 COMBINED/SEPARATED 恢复。
- 正文页默认/最大值、跨 chunk/offset 续读、UTF-8 序列化上限、可信引用、覆盖范围与跨 snapshot。
- 审查归档反例转正式测试，真正可在未修复基线复现的先记录红灯再修；不要把同写修复/用例或新功能缺实现自动表述为红绿复现。

无需为证明“支持 256k”每次真实发送 256k 材料。容量/多周期压缩边界先用隔离数据库与受控模型验证，真实模型专门验证输出质量。

### 11.2 固定真实资料任务

| 场景 | 判断标准，不只看 SUCCEEDED |
| --- | --- |
| 简单事实查询 | 不为扩容增加无关工具/模型请求，答案有必要来源 |
| 单文档逐章研究 | 真实正文充分、关键条件/数字不丢，引用准确；直接/委派均可交付 |
| 固定四文档对照 | 不再因 8 工具/30k 子输入常量只拿提纲；按目标阅读相关正文，未覆盖部分诚实列出 |
| 压缩后的继续研究 | 压缩前取得的固定关键事实、有效更正、来源与未完成范围仍可用；不能以总结语气掩盖信息丢失 |
| 缺资料/缺 embedding | 正文可读时走正文，检索不可用如实说明；不把环境失败当模型/预算缺陷 |

浏览器只使用 `browser-skill/bsk`，后台 `--no-focus`，只验收电脑端，完成前不关闭会话。查看真实回答、工具活动、引用、压缩过程和刷新恢复，不额外验收未改变的 SSE 可选清单。

记录实际请求模型/窗口来源、估算输入、真实 usage（可用时）、压缩前后体积/源范围、正文覆盖和输出；沿用已有持久事件/JSON 与证据文件，不建设新统计页面。

**停止条件：** 固定资料任务不因旧的小额/固定投影过早结束；真实质量不因压缩丢关键证据；新旧恢复/暂停/权限边界不回归。模型仍可能选择不委派、必要时回读原文或未读完巨大资料集，这些不自动成为下一轮必须继续扩建的需求。

## 12. 为什么逐步增长仍有每次请求的窗口

### 12.1 当前项目不是服务端无限追加上下文

源码复核的实际链条：

```text
本轮数据库状态/步骤
    -> Composer 新建 messages，选择历史和工具结果
    -> NativeToolCallingExecutor 创建 ModelTurnCommand(messages, tools)
    -> Adapter 将完整选定 messages/tools 序列化进这一次 HTTP 请求
    -> 返回模型文本/工具调用并落库
    -> 执行工具、保存结果
    -> 下一轮从数据库重新组装 messages，发下一次请求
```

- [Composer](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/application/runtime/AgentModelMessageComposer.java:208) 每轮创建新的消息列表，工具观察和历史经过选择/投影，因此当前实际输入不保证严格单调增长。
- [Native 入口](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/application/runtime/NativeToolCallingExecutor.java:62) 传入选定消息；[OpenAI-compatible 请求](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/infrastructure/ai/model/OpenAiCompatibleModelAdapter.java:399) 逐条序列化消息，并发送工具定义。`max_tokens` 控制本轮输出，不是应用的 50k 输入限额。
- [轮次记账](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/infrastructure/repository/AgentRunEventRecorder.java:787) 按本次 input usage 累计，并非只记本轮新读材料。已有 call/session correlation 身份不等同于提供商保存无限模型历史。
- 页面看起来是一次连续 Agent 回答，底层可以经历多次模型请求。流式正文只是当前响应逐步生成/展示，不能让下一个模型请求自动记住全部前文。

三个不同量必须分别命名：

| 量 | 含义 | 是否自然单调增长 |
| --- | --- | --- |
| 活跃上下文 C | 下一请求实际需要看到的当前视图 | 未压缩时通常增长；摘要/去重/目标改变后可变小 |
| 本轮输入 I | 本次请求实际输入 usage，包含重复发送的历史/规则 | 每轮重新计算，不应按与上一轮的差值记账 |
| 累计消耗 U | 本运行各次模型/摘要/回收子调用的实际消耗之和 | 只增加，不因压缩减少或清零 |

数学示意，不是本轮模型实测：若三个请求的输入分别为 20k、25k、30k，第三次窗口里最多是这次的 30k 输入（另留输出空间），累计输入却是 75k。当前累计 50k 限制会在此前收尾/拒绝，不能把这种现象解释成 1M 模型已经装不下。

### 12.2 本地课程与官方资料的依据

- 本地 [3.2_managing_messages.ipynb](E:/project/LangChain_Official_Course/lca-lc-foundations/notebooks/module-3/3.2_managing_messages.ipynb) 用 `SummarizationMiddleware(trigger=("tokens", 100), keep=("messages", 1))` 演示按消息体积触发摘要并保留近期原文；100 是教学阈值，不是模型硬窗口。该文件的中文注释和模型替换是本地改动，不能冒充全部为上游原版。
- OpenAI 官方说明手动多轮请求通过消息重放延续状态，并区分一次请求的上下文容量与多次调用；服务端状态引用也不代表无限模型窗口。[Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)
- 官方 compaction 按上下文体积触发整理并携带状态进入后续窗口；独立压缩输入也必须满足模型窗口。其 Responses 压缩项可能是不透明加密状态，不等同于本项目可见的文字摘要，也不保证当前各第三方模型支持该 API。本项目借鉴的是触发/保留/继续工作机制，不直接迁移接口或框架。[Compaction](https://developers.openai.com/api/docs/guides/compaction)

### 12.3 输出上限与应用累计额度不是一回事

主流 API 的 max_tokens 一类参数限制本次生成，而非替应用约束整个 Agent 多次请求的输出总和。Claude 官方 Messages API 明确把 max_tokens 定义为本次生成的最大 token 数，并单独返回 usage；这证明该参数的作用域，不证明所有提供商的思考/输出计算、账号限速和额度策略完全相同。[Messages API](https://platform.claude.com/docs/en/api/messages/create)

本项目模型配置的单次最大输出与 agent_run.max_output_tokens 的整轮额度是两层不同限制。新设计撤销后者的准入/停机作用，不撤销前者；思考消耗是否包含在单次输出内按提供商适配处理。单次输出封顶也不意味着未完成任务需要一个“继续”按钮，仍由既有自动推进/显式用户输入续跑规则处理。

**本轮修订核心口径：上下文逐步增长，约 256k 整理一次；单次请求守当前模型真实容量与输出上限；累计输入/输出只统计，不限额；建议父子独立、有限执行，保留权限、幂等、暂停、恢复与单次超时保护。**
