# Agent 预算与暂停恢复设计（简化版）

日期：2026-10-05。调查基线：d5f09ab，分支 codex/context-foundation。状态：设计方案，尚未实现。

后续用户明确要求 Agent 中途可以按当前配置换模型，并要求只做设计。最新规则与优先级见 [Agent 体验设计](E:/project/ai-collab/docs/agent-experience-design.md)；本文关于固定本运行配置的旧建议已被替代。

本文仅描述后续方案，尚未实现新的预算处理、暂停或恢复计时。本轮已实施的存量精简另见 [复杂度审查](E:/project/ai-collab/docs/agent-implemented-complexity-review.md)。此前已完成的稳定性修复结论继续有效。原方案把多种后续能力绑在一起，增加了当前需求尚不需要的状态、配置和同步关系；本版缩减第一阶段的范围。

用户已明确选择：暂停 Agent 的后续动作，已受理的后台规划继续完成；恢复时直接读取结果。

用户进一步明确：失败自动重试与断点恢复是核心 AI 能力。简化针对重复状态、闲置抽象和多套决策规则，不能以减少代码为理由删掉这些能力。预算到限后的续接仍属于需求；与同一运行的暂停恢复分开交付，是为了让各项能独立验收，并非取消该需求。

## 1. 设计复审结论

项目规模和用户目标决定需要读取哪些内容；模型容量决定一次请求能装多少内容。前者通过现有数据库工具、文档检索、章节读取、摘要和结果投影处理，后者采用统一的请求限制与网关反馈。无需为每个模型设计一套 Agent 策略。

| 原设计增加的复杂度 | 本版决定 | 原因 |
| --- | --- | --- |
| 逐模型、逐请求形态校准 token 估算 | 删除本阶段工作；沿用现有公共估算和必要余量 | 当前目标是减少无关输入并正常恢复，不需要维护校准样本和型号规则 |
| 扩充模型窗口型号清单、自动识别窗口 | 不扩充；已配置的窗口值继续作为可选限制 | 容量数值属于接入参数，不能演变成逐型号编排逻辑 |
| 按业务阶段再筛一层工具，另建阶段映射 | 第一版不做；沿用 skill 和权限过滤，先正确计入工具说明开销 | 新过滤规则会增加误隐藏工具和阶段判断错误 |
| 新增 checkpoint 表、七种恢复阶段、独立 revision 和 constraintsDigest | 删除；恢复位置以已有模型轮次、调用记录和业务操作为准 | 重复保存事实会产生新的同步和迁移问题 |
| 暂停增加独立 10 秒宽限、强制中断、迟到结果收集 | 第一版改为动作边界暂停，沿用现有请求超时 | 少一套计时器和中断语义；暂停速度的限制必须向用户说明 |
| 普通重试和跨运行续接同时扩展 | 保留现有重试；跨运行续接单独列为后续需求 | 动作身份、来源引用和不同续接模式显著放大范围 |
| 自动识别任意“继续并修改要求”的表达 | 先做明确的暂停/继续入口，纯“继续”仅路由当前唯一暂停运行 | 恢复控制与普通用户要求分开，避免覆盖目标 |
| 新租约时长、宽限时长、自动恢复次数等同时新增配置 | 首轮复用现有参数，只保留确有必要的内部默认值 | 先验证行为，再开放有实际运维需求的配置 |
| 新增多个预算等级、按项目大小自动提高总额度 | 不做；保留已有上限，先改善内容选择和到限反馈 | 项目大应按需分批读取，不能用无限增加额度代替设计 |

以下机制属于正确性要求，仍保留：业务动作防重复、旧 worker 隔离、权限与资源版本校验、当前请求与有效约束保护、暂停意图落库、请求超时及运行上限。

原生工具调用和 Legacy 路径已有功能差异，继续由现有模型网关处理。本版不增加新的提供商专用编排分支。

## 2. 用已有记录恢复，不再建设通用工作流引擎

| 已有记录或机制 | 本版用途 | 源码 |

| agent_step 的完整模型轮次 | 恢复已生成的内容与工具清单 | [recordModelTurn](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/infrastructure/repository/AgentRunEventRecorder.java:559) |
| agent_tool_invocation 的身份、参数、结果 | 判断哪些调用已完成、哪些待处理 | [knownInvocationResult](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/infrastructure/repository/AgentRepository.java:297) |
| agent_planning_operation / agent_approval | 核对业务已经受理的效果，恢复原对象 | [AgentPlanningOperationService](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/application/AgentPlanningOperationService.java:25) |

恢复只回答四个问题：

1. 当前运行是否允许执行，当前 worker 是否持有有效租约？
2. 是否有已经持久化但尚未处理完的模型工具清单？
3. 清单中的调用是否已经有结果，或业务操作已经受理？
4. 没有剩余清单时，是否可以进入现有下一轮模型调用？

将判定集中放在现有协调器/工具执行路径，避免新增一套持久阶段状态机。模型网络调用不放进数据库长事务。

“已完成不重做”指已保存的结果或已提交的业务效果。未落库的只读计算可以重新执行；半截模型输出可以重新生成。业务写入必须先核对原 invocation / operation / proposal，结果不明时给出准确失败原因，不盲目重放。

## 3. 第一项交付：把请求装小、装完整

复用 AgentContextBudget、Composer、Coordinator 和现有 RAG，不新增预算服务体系。

- 使用现有公共估算方法，先为本轮实际工具定义和附加指令留空间，再装消息；最终校验完整请求。
- 继续保护当前请求、有效约束、必要对象身份与版本。旧历史、重复结果、无关内容按剩余空间选取。
- 保留一次有界重组，减少盲目的 0.6 缩减；不能删掉当前要求来获得“请求成功”。
- 沿用已有文档相关度检索、来源数量上限、章节读取和有界摘要。必要时分批查询，不新建 RAG 调度器或自动相关性评分引擎。
- 规划业务集合增加总量与有界摘要。首轮采用明确范围和稳定排序；没有任务范围时展示概览，不声称已审查全部任务。相关对象不足时使用现有查询补充。
- 成员/任务裁剪不得改变服务端合法 ID、权限和业务版本校验。必要成员 ID 通过现有白名单服务核验。
- 第一版沿用原 skill 工具集合；精简重复说明须保留参数及出错反馈，不引入新的业务阶段工具白名单。

模型接入采用统一规则：每轮按当前配置解析模型能力与窗口值；已明确配置的窗口值可收紧请求，未配置时使用现有应用上限。默认 50000 是应用配置值，不能保证任何模型都能接收；小窗口模型可以配置一个限制数值，但无需维护其独立 Agent 流程。不增加型号数据库、自动窗口探测、tokenizer 插件或逐模型校准。

提供商拒绝输入时准确报告原因，不把输出截断当成输入超额，不自动调大额度或静默切换模型。针对新的提供商行为，只有实际失败证据出现后才决定是否补统一处理。

到限反馈只分三类：

| 原因 | 用户可采取的动作 |
| --- | --- |
| 必需输入仍然放不下 | 拆分目标、缩小资料范围；不反复重试相同大请求 |
| 本次运行时间、步骤或累计额度已耗尽 | 查看已完成与未完成结果；现阶段提供原有重新尝试 |
| 重复操作没有进展或关键资料缺失 | 查看具体阻塞原因，补充信息 |

不增加多个产品预算等级，不把 token 或执行 epoch 放在普通用户操作里。精确金额结算继续留在原待办。

## 4. 第二项交付：修正重启后的时间计算

当前 RuntimeJob 给 6 分钟租约，而规划运行最多允许 5 分钟；claimNext 接管过期 RUNNING 时，累加旧 claim 到租约到期的时间。因此程序停止等待也可能耗尽额度。这是源码推导，本次未重新故障注入。

最小修正保留现有租约和 active_elapsed_ms，只补持久存活时间及轻量续租：

- 正常结束/排队/暂停时累计本段实际执行时间；崩溃接管只累计到最后持久存活时间。
- 心跳独立于同步模型请求执行，按原 run / leaseOwner / claim epoch 续租，不增加业务 version。
- 沿用现有模型与工具超时、运行时长限制、持久恢复计数，不建设通用任务监控或自动预算重置。
- 首轮保留原租约时长；心跳采用一个内部默认间隔。真实中断验收后再决定是否需要缩短接管等待，不先承诺 60 秒恢复。
- 最后心跳间隔可能少记一小段时间，这是估计误差；不为追求精确时间建设第二套账本。
- 旧 worker、过期租约不能续租或提交；工具执行线程显式携带同一个 claim epoch。

隔离检查要覆盖现有受控业务入口，必要的锁顺序调整属于防止重复写入的修复范围。等待用户、等待审批、暂停、停机期间不计实际执行时长。

## 5. 第三项交付：在动作边界暂停、继续

第一版暂停语义：暂停请求落库后，不再启动新的模型、摘要、工具或提案；已经开始的模型调用或工具执行按现有超时结束，保存完整结果后暂停。并行批次里已派发的调用属于在途动作，尚未派发的调用继续保留。

用户看到“正在暂停，当前调用结束后保存进度”，不承诺立刻中断网络请求。确需更快停止时沿用取消入口；取消仍为终态，不冒充可恢复暂停。快速中断作为以后有实际需求时再评估的独立能力。

最小新增持久控制信息为 PAUSED 状态和 pause_requested_at；第二项交付增加 last_heartbeat_at。用户要求版本优先复用现有 goalVersion / 消息身份，恢复所需关联写在原运行或模型轮次元数据中。无需新增 checkpoint 表、七种 phase 或约束摘要哈希。

具体要求：

- QUEUED 暂停原子转 PAUSED；RUNNING 先记暂停意图，由 worker 在动作边界转 PAUSED。
- 暂停请求与新业务受理通过同一运行锁确定先后：业务先受理就完成原事务，暂停先到就不启动该动作。
- 暂停时释放租约并使旧 epoch 无效，保留未完成工具调用。不能调用现有 requeueRun 的批次结束逻辑，把 PENDING 全标为 SKIPPED。
- 恢复 PAUSED 仅转 QUEUED，继续同一 run；不清空已用额度，不新建结果副本。
- 先核对已受理业务动作，优先执行原清单的待处理调用；无待处理调用时走原模型路径。
- 有已持久化完整模型结果时不重发同一模型请求。仍在生成且未保存的内容可重新请求。
- 完整无工具模型回答已保存时，恢复应完成其校验与最终记录；不能因为没有待处理工具就重发模型。
- 暂停后进程退出，接管先读暂停意图，转 PAUSED；不自动开始新动作。
- 重复 pause/resume 返回当前有效状态；CAS / 行锁及原领取逻辑保证只有一个 worker 推进。
- 最终完成和暂停竞争时以事务提交顺序为准，已完成保持原终态，不改成暂停。
- 等待用户输入/审批继续使用原入口，不把“继续”当审批。
- 已受理后台规划独立继续，恢复读取原 operation。Agent 已结束时不再提供暂停按钮。
- 首轮覆盖用户直接发起的根运行，子 Agent 全树暂停单列待办。

普通“继续”只在当前会话能唯一对应当前目标的 PAUSED 运行时路由到 resume；按钮与文本共用相同命令。纯控制消息不经过普通 appendUser 去覆盖 latestRequest 或清除待回答问题。

用户要求发生变化时，先核对已提交动作，再使旧未执行参数失效，使用现有普通模型路径处理最新要求与已有事实；不可直接重放旧清单。版本判断采用用户消息/goalVersion，避免摘要更新导致误判；不新建 constraintsDigest 校准体系。不承诺首轮自动识别所有“继续并修改要求”的自然语言。

权限和资源版本沿用原工具业务校验；遇到撤权、对象失效、配置不可用时准确反馈。用户可以更改模型配置，后续模型轮次按当前配置执行；不增加系统自行择模或自动修复业务对象的能力。

前端复用 run detail、事件及 d5f09ab 的作用域保护；刷新重读数据库，迟到响应必须匹配项目、会话和请求代次。内部恢复位置可由原步骤派生供诊断，不增加第二套页面恢复数据源。

## 6. 本轮明确延期的能力

跨运行“继续剩余任务”暂不加入第一阶段：它需要跨运行关联动作身份、旧来源引用、新额度和并发语义。保留现有终态重新尝试，清楚说明它创建新运行，不能宣传为断点续跑。

任意外部写工具恰好一次执行、子 Agent 全树暂停、强制即时暂停、逐模型容量校准、自动多级预算、通用自然语言恢复识别继续列为待办。用户后续需要且有实际案例时分别立项。

## 7. 每项交付独立验收与收尾

| 交付 | 必须验证 | 收尾边界 |
| --- | --- | --- |
| 请求体积 | 工具开销占主要输入；当前要求尾部含限制；大项目集合；摘要失败保旧内容 | 完整请求受控、必要内容与权限不退化，即可收尾 |
| 恢复计时 | 真实进程中断；心跳前后中断；旧 worker 迟到；请求挂起仍按超时结束 | 停机等待不耗额度、旧执行不能重复提交，即可收尾 |
| 暂停继续 | 模型已落库；部分工具已保存；业务受理后 Agent 记录前中断；无工具完整回答；暂停/完成/取消竞争；重复恢复；切换会话 | 原目标和有效要求正确、已提交动作不重做、暂停等待不耗时，即可收尾 |

数据库竞争使用真实 PostgreSQL，时间测试使用可注入时钟和同步点。恢复计时另做一次隔离宿主真实进程中断，不用改数据库时间代替真实中断。浏览器验收统一使用 browser-skill/bsk。

真实模型只补与本项变化直接相关的少量目标验收。没有新失败证据时不反复重跑完整 24 轮，不把延期能力加入上述交付门槛。

三项按顺序独立提交；不改已发布迁移，不合并 main、不部署、不操作业务数据库。本文只是下一阶段方案，尚未实现暂停或新的恢复计时。
