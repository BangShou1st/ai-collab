## 2. R1：修复崩溃恢复计时

### 已核对的触发链

- `AgentRuntimeJob.tick` 使用 6 分钟租约。
- `AgentRepository.claimNext` 接管过期 RUNNING 时，将旧 claim_started_at 到 lease_expires_at 的时间累加到 active_elapsed_ms。
- `AgentRuntimeCoordinator.advance` 先检查 `min(300000, Skill.maxRunDuration) - activeElapsedMillis`，然后才进入已保存结果恢复。

因此，即使 worker 很快退出，接管也容易因等待租约的时间直接触发 BUDGET_EXCEEDED。先用确定性测试确认该链，再修改实现。

### 要达到的行为

- 已确认的有效执行时长继续保留；排队、重试等待、进程离线和租约到期等待不冒充执行时间。
- 正常运行、正常轮次结束、自动重试与接管使用同一套可说明的累计语义。
- 当前活跃请求仍有 deadline，真实执行超时仍受保护，不能通过恢复把已耗时全部清零。
- 租约/claim_version 的旧 worker 拦截仍生效；时长记录本身也不能让旧 worker 修改新 claim 的状态。
- 原有步骤、输入/输出限额和重试次数保护保持，不靠调大限额或取消检查让测试通过。

### 设计约束

先检查已存在的 active_elapsed_ms、claim_started_at、轮次和调用记录能支持哪些可靠证据，再确定最小修法。重点是“租约有效期不等于已执行时长”。如果当前持久记录不能精确获知退出时间，要明确记录粒度及未确认尾段的误差/边界，不虚称精确计时。

优先复用现有状态、在明确推进边界记录时长；若确需少量持久字段，说明用途并按迁移约定添加。不要为本问题建立独立计时服务、分布式心跳平台或通用执行框架，也不要引入散落多处的第二套时间预算。实现应由清楚的时间计算与持久化边界维护。

### 核心验收

使用隔离 PostgreSQL 的受控时间/数据库状态构造，避免真的等待 6 分钟：

1. 少量已执行时间后退出，租约过期再接管，离线等待不累计，运行能够进入已有进度恢复。
2. 多次接管不重复累计、不清除既有已确认时长。
3. 正常轮次结束和自动重试计时一致，等待时间不累计。
4. 已真实耗尽时长的运行仍会正确到限。
5. 新 worker 接管后，旧 claim 的业务提交及时长更新均不能污染新状态。

## 3. R2：复用已持久化模型结果完成收口

### 已核对的窗口

协调器先调用 `recordModelTurnWithSettlement` 保存 MODEL_TURN 与调用结算，再分别处理工具、[QUESTIONS]、预算部分回答或普通最终文本。`pendingModelTurn` 当前只搜索 toolCalls 非空且 batchHandled 未完成的轮次。

无工具调用的响应若在“MODEL_TURN 已提交 → 最终处理尚未提交”之间退出，当前恢复入口无法复用它，可能重新请求模型。先构造这个真实提交窗口验证风险。

### 要达到的行为

- 已保存且尚未消费的有效响应，在接管后先用于继续其原本的后续处理，不能因为遗漏恢复分支再次请求模型。
- 普通最终文本按原有规则收口；[QUESTIONS] 仍进入 WAITING_FOR_USER_INPUT；预算强制收尾且核心动作未完成的文本仍是部分完成/预算终态；空内容和无效响应维持原错误语义。
- 保存的结果不能绕过已发生的取消、业务权限、租约/版本和真实输入/输出超限检查；同时不能为了无需新模型调用的收尾重新消耗请求预留或重解析模型配置。
- 接管前后结果消费恰好一次：最终消息、终态步骤和对应事件不重复，用量不再次累计。
- 工具轮次恢复、已完成 invocation 复用、原 source_mode 权限语义保持。
- 模型配置在结果保存后更改、禁用或删除，不应单独使一个无需再调用模型的有效结果丢失；未来确需新请求时仍按当前配置解析。

### 设计约束

优先复用已有 MODEL_TURN、调用身份、批次消费标记和原子结果写路径。可选择最小的原子收口调整或补齐已保存结果的恢复分支，以实际证据决定；需要考虑工作区/数据库中已有未收口文本结果的兼容。

正常处理与恢复处理应共享相同的结果判定，避免复制两套收尾逻辑。不要简单“查询到任意文本就记成功”，也不要让旧轮次、已消费轮次或其他运行的结果被再次使用。若某种原始处理意图无法从已有记录可靠还原，只补必要的显式元数据，不建立全套 checkpoint 表或新的状态机体系。

保持同事务内的状态、步骤、消息与对应事件一致，不拆散 Recorder 的原子操作，不扩建计费逻辑。

### 核心验收

使用真实 PostgreSQL，先确认 MODEL_TURN 事务已提交，再在最终收尾前受控中断并切换 worker。使用同步点/测试代理模拟退出窗口，不给生产增加测试专用执行引擎，也不靠长 sleep：

1. 普通文本恢复成功，模型零新增调用，最终回答/步骤/事件各一次。
2. 重复接管或重复推进不重复消费或记账。
3. [QUESTIONS] 恢复到等待输入，预算部分回答保持原状态语义。
4. 已取消、已有终态、旧 claim 迟到提交、旧/已消费轮次均不能越界生效。
5. 保存后更改模型配置无需重新调用模型；需要下一次新请求时仍使用当前配置。
6. 既有工具批次恢复与来源模式校验回归继续通过。
