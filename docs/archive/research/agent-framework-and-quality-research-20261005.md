## 2. 真实回答链路中需要优先处理的内容

### 2.1 已做函数复现：投影后的任务续页会跳过未读记录

`list_tasks` 默认返回 20 条，最多 50 条，用本页最后一条的 ID 生成 `nextCursor`。组装器对超过长度阈值的结果使用通用投影，每个数组只留前三项；标量中的 `returned`、`hasMore`、`nextCursor` 保留原值。

用现有 `target/classes` 中的实际 `AgentModelMessageComposer.projectToolOutput` 做反射调用，输入构造为 20 条任务、总数 40、6000 字符阈值，输出：

```json
{
  "originalChars": 8064,
  "visibleTaskRecords": 3,
  "declaredReturned": 20,
  "nextCursor": "00000000-0000-0000-0000-000000000020",
  "lastVisibleId": "00000000-0000-0000-0000-000000000003"
}
```

因此，模型按这个游标继续查询会从第 21 条开始，跳过本页第 4–20 条。投影标记能提醒模型结果不全，但不能自动修正游标。模型重新用更小 limit 从原游标读取可能补救；当前协议没有保证它这样做。

- [任务分页](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/infrastructure/tool/TaskListAgentTool.java:55)
- [通用投影入口](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/application/runtime/AgentModelMessageComposer.java:460)
- [数组裁剪](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/application/runtime/AgentModelMessageComposer.java:546)

设计建议：首先把列表工具的返回页控制在合理体积内，减少重复字段；仍需投影时，让模型可见记录、可见条数和续读位置保持一致。保留服务端原始结果及原调用身份。不要建设通用 RAG 调度器，也不要要求模型自行推算丢失的范围。回归应验证多页串联后没有遗漏，而不是只断言存在 `projection` 标记。

### 2.2 已从源码确认：里程碑列表没有续页能力

`list_milestones` 只接受 limit，默认 20、最大 50，返回 `items` 和 `truncated`，没有 cursor、下一页入口或总数。因此仅靠这个工具不能遍历超过 50 条的里程碑。真实大项目的“检查全部里程碑”存在能力缺口。

- [里程碑列表](E:/project/ai-collab/ai-collab-backend/src/main/java/com/shitulelv/aicollab/agent/infrastructure/tool/MilestoneListAgentTool.java:30)

设计建议：按现有任务列表的方式补一个简单、有稳定排序的分页契约，包含范围和总量信息。具体日期/状态过滤是否增加，由典型问题和实际数据规模决定。

### 2.3 已确认的裁剪与收尾机制，不能全部称为缺陷

| 现有机制 | 影响 | 如何评价 |
| --- | --- | --- |
| 最新工具结果 6000 字符、较旧结果 1500 字符；超限投影字符串和数组 | 细节可能无法进入模型本轮输入 | 大结果需要分页与明确覆盖范围；不能靠全文塞入解决 |
| 工具清洗器 32 KiB 上限及二次缩减 | 部分内容在持久化前已经被缩减 | 脱敏与体积控制需要保留，分页语义须与缩减一致 |
| 运行累计输入额度及最终请求预留 | 有成功工具结果后，可能提前清空工具列表并强制回答 | 属执行保护，但资料还不够时必须明确部分完成 |
| Skill 输出模板与多处追加指令 | 回答内容受模板、目标范围和收尾指令共同影响 | 应消除冲突，围绕用户问题按需组织回答 |

例如 `ProjectHealthSkill` 要求第一轮并行调用全部所需工具，而通用提示又强调最少必要工具；`DeliveryReadinessSkill` 提示检查文档完整性，但当前白名单只有进度、任务、里程碑和概况，没有文档读取工具。后者可以如实说明文档未核查，不能宣传已经完成文档检查。这是能力声明与实际工具范围需要统一的问题，不应靠继续堆提示词补救。

这些机制与截图里的固定短答案没有因果关系。是否导致某次真实回答质量不足，需要看该次问题、模型、请求输入、工具输出、投影标记和收尾事件。本轮未新增真实模型验收。

### 2.4 回答质量应该怎样验收

以截图问题“检查本周任务是否影响交付”为例，合格回答应当在已取得证据范围内说明：

1. 判断：哪些交付可能受影响；证据不足时说明还不能确定。
2. 事实：有关任务、状态、日期、负责人、所属里程碑或依赖。只列确实查到的内容。
3. 原因：任务与交付之间有什么关联，区分确定事实和推断。
4. 下一步：哪些任务应优先处理、需要谁确认或补充什么信息。
5. 范围：核查的时间范围、对象范围、是否读完分页。

不固定字数、不给缺依据的分数、不新增一个评审 Agent。列表请求保持直接，复杂分析提供足够证据和解释。资料不全时优先改查询能力，而不是强制模型写长报告。

## 3. 自主编排的维护成本为什么偏高

项目确实有通用 AI 基础设施的自研成本，也有业务正确性本来就需要的成本。不能把两者都归为“框架可以解决”。

| 层次 | 当前承担的工作 | 框架能承担什么 | 项目仍要承担什么 |
| --- | --- | --- | --- |
| 模型接入 | 多提供商消息转换、工具协议、流分片、响应解析、异常分类、usage | 成熟 SDK 可替换大量通用协议处理 | 当前配置解析、密钥归属、特殊端点参数兼容、统一业务错误 |
| Agent 执行 | 决策循环、工具批次、重试、上下文、恢复位置 | Agent/Graph 框架可接管部分循环与检查点 | 运行调度、业务恢复规则、暂停意图、实际权限接入 |
| 业务动作 | 任务/规划提案、审批、资源版本、幂等、旧 worker 隔离 | 提供工具回调和执行钩子 | 权限、审批事务、业务操作身份和防重复写入 |
| 产品体验 | SSE 重放、会话作用域、过程/最终回答、错误提示 | 框架能提供运行事件 | 事件持久化契约、页面状态与交互、真实内容质量 |

当前明显增加维护成本的地方：

- 协调器约 662 行，工具执行器约 661 行，消息组装器约 709 行，事件记录器约 1020 行。行数本身不是过度设计的证明；但请求准备、预算收尾、摘要、格式修复、恢复和结算在这些类之间相互影响，改一个边界需要跨层核对。
- 保留新旧上下文组装路径、原生工具/Legacy 协议、多个兼容重载和测试构造分支。保留有实际回退需求的路径合理；没有使用者的兼容路径会持续增加组合数。
- 工具结果有清洗、投影、历史选择多层缩减；同一列表事实又可能以 `items` 和 `taskFacts` 重复进入输入。必须明确哪个层负责范围与续读语义。
- 工作状态保护里有较多中文句式规则；继续逐句补规则会变成语义解析器。保留已验证的必要约束保护，避免无限扩张。
- 前几轮把异常用量结算边角连续作为交付门槛，拖长了收尾。接下来先保证核心体验，精确费用仍留待办。

应该保留的机制：租约隔离、受控写工具、项目权限、审批、资源版本校验、业务操作幂等、当前目标保护、完整历史记录。删掉这些可能减少代码，但会破坏用户需要的可靠性。

## 4. Java/JVM 框架调查

调查范围覆盖主要相关方向，不声称穷尽所有 Java AI 库。以下是截至本次访问官方资料的判断，功能、版本兼容和迁移收益应分别验证。

### Spring AI：优先评估模型接入层

Spring AI 提供统一模型接口、工具调用、流式和 ChatClient 扩展机制。2.x 将工具循环放在 ToolCallingAdvisor 中，也支持应用控制工具执行。它能减少接入层重复代码；采用低层模型接口时，应用仍需自行推进运行。官方工具调用文档明确讨论外部审批与运行控制场景。[工具调用官方文档](https://docs.spring.io/spring-ai/reference/api/tools.html)

本项目为 Java 21 / Spring Boot 4.1.0；官方说明 Spring AI 2.0.x 支持 Boot 4.0.x 和 4.1.x，版本方向匹配。[版本支持](https://docs.spring.io/spring-ai/reference/getting-started.html)

ChatMemory 管理送给模型的记忆，并不替代完整会话历史。本项目的用户历史和业务记录要保留，不能直接交给窗口记忆淘汰。[ChatMemory 与历史](https://docs.spring.io/spring-ai/reference/api/chat-memory.html)

判断：值得优先验证。仅替换模型调用不会自动减少协调器中的恢复分支，也不会提高答案信息量。

### LangChain4j：模型与 Agent 的另一条选择

提供 Java 模型接口、AI Services、工具、RAG 和 ChatMemory。当前官方有 Spring Boot 4 专用 starter，不能再以“只支持 Boot 3”为理由排除它。[Spring Boot 集成](https://docs.langchain4j.dev/tutorials/spring-boot-integration/)

当前 Agentic 文档提供持久 AgenticScope、每步检查点和 planner 位置恢复，也支持人在回路；同一文档仍把整个 agentic 模块标为 experimental。不能声称它没有恢复能力，也不能把这些能力直接视为本项目已经验证可用。[Agentic 官方文档](https://docs.langchain4j.dev/tutorials/agents/)

判断：可以作为 Spring AI 的替代候选；不同时引入两个 SDK 管同一条链路。复杂 Agentic 模块本轮不直接大规模迁移。

### Spring AI Alibaba：Agent 与 Graph 能力贴近需求，版本先核对

ReactAgent 提供模型/工具循环、调用次数限制和人工确认扩展；Graph 提供检查点、暂停及恢复。[ReactAgent 快速开始](https://java2ai.com/docs/quick-start/)

持久化执行文档也明确：恢复从节点开头开始，业务副作用需要幂等键或核对已有结果。这能减少执行位置管理，却不能替项目消除重复业务写入风险。[持久化执行](https://java2ai.com/docs/frameworks/graph-core/examples/long-time-running-task/)

本次查看的主分支 POM 为 Alibaba 1.1.2.2、Spring AI 1.1.2、Boot 3.5.8，与当前应用 Boot 4.1 存在版本对接风险。这是所查分支的依赖事实，不是“所有版本均不支持 Boot 4”的断言。[主分支 POM](https://raw.githubusercontent.com/alibaba/spring-ai-alibaba/main/pom.xml)

判断：功能值得参考；不为它先降级整个应用。选用前需证明目标发布版本的依赖兼容。

### LangGraph4j：持久执行的重点候选

Graph 明确管理状态、节点、条件边、检查点、线程 ID、中断与恢复，有 PostgreSQL 检查点方向。它提供执行骨架，不会自动理解任务和审批业务。[核心概念与检查点](https://langgraph4j.github.io/langgraph4j/1.9/core/core-library/)

当前主分支包含 Spring AI 集成模块，Spring AI 属性为 2.0.1；这说明与项目技术方向相关，但不替代选择实际发布坐标后编译和行为验证。[主分支 POM](https://raw.githubusercontent.com/langgraph4j/langgraph4j/main/pom.xml)

判断：如果下一阶段重点是暂停/崩溃恢复，值得做小验证。采用后应由它承担执行位置推进，退出被替代的旧编排分支；不能两个执行引擎都决定下一步。

### AgentScope Java：完整 ReAct 执行器候选

官方 Java 2.0 文档涵盖工具循环、事件流、权限确认、状态存储、并发会话和协作中断。ReActAgent 本身也可配置状态存储，不必为了本项目引入 Harness 的工作区、子 Agent、沙箱等全部能力。[Agent 与执行控制](https://raw.githubusercontent.com/agentscope-ai/agentscope-java/main/docs/v2/en/docs/building-blocks/agent.md)

文档明确中断信号本身不持久化、运行管理器负责授权和清理；保存会话状态也不等于覆盖进程硬退出后的所有恢复窗口。[状态与运行上下文](https://raw.githubusercontent.com/agentscope-ai/agentscope-java/main/docs/v2/en/docs/building-blocks/context.md)

判断：若希望框架直接接管普通 Agent 循环，它比单纯模型 SDK 更贴近目标；作为备选，与 Graph 选一个运行所有者。需要验证每轮动态配置和硬退出后的待处理业务恢复。

### Koog、Semantic Kernel Java、Google ADK Java

- Koog 当前提供 Java fluent API、执行图、持久检查点和重试，不应只把它看成 Kotlin 库。它引入另一套执行与存储抽象；目前不是优先迁移对象。[Java 支持](https://docs.koog.ai/why-koog/)、[持久化](https://docs.koog.ai/features/agent-persistence/)、[重试](https://docs.koog.ai/prompts/handling-failures/)
- Semantic Kernel 有 Java SDK；所查官方发布页中 Java Agent 抽象与 ChatCompletionAgent 出现在 1.4.4-RC1。不能把 .NET/Python 的所有能力默认套给 Java，也不能凭 SDK 名称认为已满足本项目恢复要求。当前没有明确的 Microsoft 生态迁移需求，优先级低。[Java 发布记录](https://github.com/microsoft/semantic-kernel-java/releases)
- Google ADK Java 提供工具与多 Agent 组合、开发界面，官方仓库强调 Google 生态并标 Preview。当前需求不依赖这一生态，缺少足够迁移收益证据。[Java 官方仓库](https://github.com/google/adk-java)

### 对“维护成本会显著降低吗”的回答

我的判断是：模型协议与通用运行机制的维护成本有机会明显下降，业务可靠性和产品体验的维护仍然存在。是否降低整个项目成本，当前没有实施对照数据，不能给出百分比。

同一个项目使用多个框架是合理的，选择应按职责划分：

| 组合 | 分工与评价 |
| --- | --- |
| Spring AI + LangGraph4j | 前者处理模型协议，后者管理执行图和检查点；是本项目值得验证的组合 |
| LangChain4j + LangGraph4j | 另一种模型 SDK + 执行图组合；模型层与上一行选一个作为同链路的主要实现 |
| Spring AI + Spring AI Alibaba | 后者本来就基于前者；模型接口与 Agent/Graph 组合合理，但先解决发布版本兼容 |
| AgentScope Java + 现有 Spring 业务服务 | AgentScope 管 Agent 执行，Spring 服务管业务；不必再额外套一层同职责 Agent 引擎 |
| 同项目不同功能分别使用 Spring AI / LangChain4j | 可以，例如独立功能有不同集成需求；须评估额外依赖、配置和运维成本，避免同一次请求穿过两个重试循环 |

每次模型请求的配置选择、每个工具调用的执行、每次重试的计数、每个运行的恢复位置，各有一个明确负责者即可。完整历史、产品运行记录、框架检查点可以承担不同用途，但不能分别保存同一恢复阶段再互相猜测同步。

只把现有协调器包在框架外面，保留自研循环、重试、恢复，再叠加框架循环和检查点，成本可能上升。真正的替换必须列出哪些已有职责由框架承担、哪些分支可以退出、哪些业务记录仍是权威来源。

我调整此前“暂不引框架”的笼统建议：优先验证通用接入替换；在继续扩大自研暂停/恢复之前，对持久执行做一个有边界的框架验证。现在不直接推倒已有系统。

## 6. 建议的开发顺序与停止边界

### 第一件事：把当前中断修复变成可验收基线

接手者保留全部未提交代码，先完成既有后端 PG 回归，再核对准备链仍存在的配置重读，完成前端两项。一次有范围的完整回归用于当前协调器、记录器和迁移变化；只补受影响交互验收，不重做 24 轮。通过后单独收口，不能带入下面的框架或暂停开发。

### 第二件事：单独修资料可读完整性并验答案

任务列表、里程碑列表优先。用超过一页的可追溯数据证明分页和投影没有漏读，验证“概览”“列全部”“查交付风险”三种问题的不同范围。保持脱敏、权限、必要输入保护。之后用当前真实配置做少量针对性质量验收；不能继续把固定假答案截图当成分析质量证据。

质量标准看事实、原因、建议和范围，不看字数。停止边界是这些代表问题能取得必要资料并据实回答，不是增加通用评分器或第二个模型审查链。

### 第三件事：在独立小样里验证框架替换收益

优先方向：Spring AI 2.x 模型接入；持久执行先验证 LangGraph4j，与 AgentScope Java 作为可替代执行器比较。不要把八个框架都安装进业务项目。

验证用同一组任务、现有工具服务、同一假模型和隔离持久存储，重点回答六个问题：

1. 当前配置能否在每次请求边界生效，准备、发送和结果模式一致？
2. 正文与工具调用混合、流分片、格式失败和截断如何统一转换为现有返回/错误契约？
3. 重试由谁负责，次数与耗时是否有界，能否避免 SDK 和运行层都重复重试？
4. 保存模型结果后退出、业务已受理但执行记录未保存时退出，重启是否恢复正确且不重复业务效果？
5. 暂停、人工确认和取消能否符合本项目语义，已受理后台规划是否继续并复用原 operation？
6. 框架事件能否通过薄适配落成现有事件序号，刷新重放后过程和最终回答不重复？

必须输出“可替换的现有职责清单、保留的业务规则、需要的适配代码、已覆盖/未覆盖边界”。持久恢复不能用 InMemorySaver 演示替代。无需同时开新 UI 或引入多个运行状态系统。

采用条件：同样的关键行为通过，能实际退出原有通用实现，业务服务和原操作身份保留，只有一个执行器决定下一步。没有证明净减少维护职责就不迁移，不以新增依赖或代码行数单独判定成功。

### 第四件事：按选定执行基础补核心体验

依次处理崩溃后的有效时长、同运行暂停继续、重试状态显示、完整请求体积计算；跨运行剩余工作续接另立小任务。每项都有独立验收终点。逐字流式、精确费用和自动择模后排。

本项目的业务目标不需要重新推翻。需要收敛的是通用 AI 基础设施的自研范围、重复分支、信息覆盖契约和验收口径。暂停当前开发做这次检查是合理的；下一步应围绕有证据的缺口和可验证的替换收益继续。
