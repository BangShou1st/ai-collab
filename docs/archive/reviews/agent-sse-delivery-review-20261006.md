## 2. 剩余的同一个隔离问题

### 2.1 持久事件仍会被临时写入的共享锁阻塞

`AgentEventStreamService.drainContent` 在 `synchronized(subscription)` 内执行网络写。`publish → send` 仍由调用线程同步获取同一把锁。`AgentEventService.append` 的 `afterCommit` 又在原事务调用线程上同步执行 `streams.publish`。

因此：临时帧慢写占锁 → 模型读取可返回 → 记录完整模型结果的事务提交 → afterCommit 等锁 → Agent 调用无法返回并进入后续结果消费/最终回答阶段。数据库事务已经提交，不意味着 worker 已完成推进。一个慢订阅者排在 fanout 前面时，也会拦住后面的健康订阅者接收持久事件。

确定性探针 `reviewBlockedPreviewMustNotBlockPersistentEventPublication`：先用 latch 确认临时帧发送确实占住连接；再发布 MODEL_COMPLETED，同时注册一个健康订阅者。释放慢写之前，**publish 没有返回，健康订阅者没有收到持久事件**；释放后任务才能返回。不是假设，也没有等待真实网络。

### 2.2 heartbeat 仍直接占用调度调用线程

`heartbeat` 直接调用 `emitter.send`，没有进入异步发送器。确定性探针 `reviewHeartbeatMustNotWaitForSubscriberNetworkWrite` 确认：写入已发生且被阻塞时，heartbeat 调用不能返回，只有释放慢写才返回。

这已经足以说明网络写会占住调度调用线程。当前运行 job 同样使用 `@Scheduled`；是否拖延其他 job 取决于实际 scheduler 配置，本次没有启动 Spring 上下文，不把全局调度停滞写成已实测结论。

重点是调用线程隔离，不依据“heartbeat 没拿业务锁”直接断言 SSE 字节必然交错；框架内部也可能对写入加锁。

## 3. 唯一剩余开发任务：统一订阅发送入口

沿用 `AgentEventStreamService`，把**持久事件、正文预览、heartbeat、replay** 纳入同一个订阅发送机制；真正网络写只发生在专用发送线程。

### 3.1 最小职责

- `publish`、`publishContentDelta`、`heartbeat` 只做非阻塞投递/唤醒，不等待网络、发送锁或 Future，不让线程池饱和走 CallerRunsPolicy。
- 每个订阅只有一条串行写出路径，同一连接的帧顺序由这里管理；模型线程、事务提交回调及 scheduler 不能在连接锁外/锁内保留同步网络旁路。
- 保留当前进程内共享、有界线程资源和单槽累计预览的方向，不为每个 token/运行/连接无限创建任务或线程池。
- 临时预览可合并、舍弃；heartbeat 只保留待发送意图即可，不用不断积压。容量和清理规则必须明确。

### 3.2 持久事件与游标

- 持久事实仍以 `agent_event` 为准。不用“线程池饱和就丢一条持久事件、继续推进游标”掩盖过载。
- 选择简单的有界持久队列，或轻量唤醒后由发送端按数据库游标有序追赶；后一种可以直接复用现有 `events.list`。不要叠加通用消息平台。
- replay 与实时发布必须共用顺序规则。并发 afterCommit 到达顺序不等于数据库 sequence 顺序，不能先发较大序号、再因为 lastSequence 跳过已经提交的较小序号。
- 持久游标只随实际写出的持久事件前进；正文帧与 heartbeat 不修改序号、Last-Event-ID 或 replay 范围。
- 队列/线程资源过载或慢连接需要退出时，只影响该订阅，让客户端用实际接收游标重新追赶；不能改 Agent 运行状态，不能在生产线程阻塞做连接清理，也不能留下永远不再调度的死订阅。

### 3.3 生命周期与兼容

- 订阅仍经现有成员/运行范围校验，不增加旁路 endpoint。
- 保留原先失败、成功、审批、等待输入等关流条件；终止事件应先按序送出再正常完成连接。不要借机改变业务终态或暂停语义。
- 关闭/移除订阅时关闭发送作用域、清理待发内容；迟到的临时任务不能复活订阅或越过新运行。
- 有界丢弃临时预览不等于模型失败。浏览器断开不取消 Agent；既有消息与结果恢复契约保持。
- 不承诺补回未提交预览。最终结果仍以持久消息为准，队列里没送出的预览允许被最终事件替代。
