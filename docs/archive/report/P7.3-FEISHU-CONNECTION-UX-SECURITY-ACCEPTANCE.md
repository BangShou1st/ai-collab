## 2. 原飞书连接流程审查

P7.2 后流程：项目 Owner/Admin 在「添加飞书文件夹」对话框创建本项目专属连接；系统管理员在页面底部管理系统连接与事件凭据；用户身份需先完成事件验证（`url_verification`）再发起 OAuth（PKCE + S256、state 哈希存储、回调固定 HTTPS 路径）；添加知识源时后端先以对应身份拉取文件夹列表与协作者校验，通过后落库；同步由手动触发或调度器触发。

审查确认的断点与风险：

1. **跨项目连接引用（确认存在，已修复）**：`ConnectorOAuthService.start()` 与 `ConnectorSourceService.create()` 仅 `connections.find(connectionId)` 判断存在与 ACTIVE，未校验 `visibility/ownerProjectId`，与 `listAvailableForProject()` 作用域不一致。项目 A 管理员可手工构造请求使用项目 B 的 PROJECT 私有连接发起 OAuth 或创建知识源（应用身份 Token 直接复用连接存储的 Secret）。
2. 项目管理员无法在项目视图查看连接状态、配置事件凭据、查看事件验证状态（入口仅在系统管理员区域），无法独立走通用户身份全流程。
3. folderToken 需手工从 URL 截取；添加失败时异常统一显示为「添加失败」类提示。
4. OAuth 返回后需手动刷新授权状态；添加知识源后需再点一次「同步」。

## 3. 权限风险与修复证据

**集中修复**：`ConnectorConnectionService.requireAvailableForProject(projectId, connectionId)`：

- SYSTEM 连接：对所有项目可用（沿用 `listAvailableForProject` 既有策略）。
- PROJECT 连接：仅 `ownerProjectId` 对应项目可用。
- 不存在、非 ACTIVE、他项目私有一律抛 `CONNECTOR_CONNECTION_NOT_FOUND`，不泄露他项目连接存在性。

`ConnectorOAuthService.start()` 与 `ConnectorSourceService.create()` 统一改用该方法；`callback()` 沿用 flow 锁定的 `projectId/connectionId/userId` 并再次校验管理员与可写状态。管理操作（verify / configureEvents / delete）继续由 `requireManageable` 强制：PROJECT 连接要求归属项目 Owner/Admin，SYSTEM 连接要求系统管理员。新增项目级只读接口 `GET /projects/{projectId}/connector/connections/{connectionId}/event-status` 同样经过 `requireAdmin + requireAvailableForProject` 双重校验。

**回归测试**（新增/更新）：

- `ConnectorConnectionScopeTest`（4 例）：SYSTEM 任意项目可用；PROJECT 仅归属项目可用、他项目拒绝；非 ACTIVE 拒绝；事件状态读取要求项目管理员且受作用域约束。
- `ConnectorSourceServiceAccessTest`（3 例）：跨项目连接在触达飞书前被拒（`listFolderDocx` 与 insert 未被调用）；非法 folderToken 拒绝；SYSTEM 连接 + 合法 Token 正常落库并审计。
- `ConnectorOAuthServiceTest` 新增：作用域拒绝时 `saveFlow` 不被调用。

对照任务 3.2 的九个场景：1（跨项目私有连接拒绝）为本轮核心新增覆盖；2（他项目事件凭据）由作用域校验 + `requireManageable` 双重约束并有测试；3（他项目用户授权）由既有 `grants.find(projectId, authorizationId)` + `grant.userId/connectionId` 校验保持，未削弱；4/5/6/7 由既有 `ConnectorConnectionServiceTest` 覆盖且本轮全绿；8（SYSTEM 共享连接可用）由 `ConnectorSourceServiceAccessTest` 第三例表达；9（手工 API 无法绕过）由「构造请求经后端作用域校验拒绝」的单元测试表达。既有项目隔离与撤权规则未改动。

folderToken 服务端格式校验 `^[A-Za-z0-9_-]{6,128}$`，兼容旧客户端原始 Token；未新增任何包含 folderToken 的日志输出；真实读取权限仍由飞书 `listFolderDocx` / `folderPermissionMembers` 验证。

## 6. OAuth 自动刷新实现

发起授权前对当前项目 + 当前连接 + 当前用户的授权做快照（grant id 集合 + ACTIVE 集合）：

- 若该连接已有 ACTIVE 授权：提示完成授权后手动刷新（重新授权会原位更新同一 grant，无法与既有 ACTIVE 可靠区分，不误报成功）。
- 否则进入受控轮询：每 3 秒调用既有 `authorizations` 接口，最长 5 分钟；出现「新 grant id 转 ACTIVE」或「既有非 ACTIVE grant 转 ACTIVE」即判定本次授权成功：停止轮询、刷新列表、自动选中新授权并提示「飞书授权成功，可以继续添加知识源」。
- 生命周期：弹窗关闭（`watch(createDialog)`）与组件卸载（`onUnmounted`）即停止轮询；单次轮询失败不终止等待；超时降级为手动刷新提示。
- 不暴露 state / code / token；未放宽跨域与 OAuth 校验；用户取消授权不会产生新 grant，不误报成功（组件测试覆盖）。

## 7. 首次自动同步实现

`submitCreate()` 在 `createSource` 成功后立即调用既有 `syncSource`：

- 成功：提示「知识源已添加，首次同步已开始」，刷新列表展示同步状态、文档数量与新增/更新/跳过/失败/移除计数（列表既有列已具备），并支持手动重新同步。
- 同步启动失败：不回滚、不重复创建，明确提示「知识源已添加，但首次同步启动失败，可在列表中点击同步重试」（组件测试覆盖两条路径）。
- 后端 `createSource` 落库前已完成文件夹读取权限验证；重复创建由既有唯一约束拦截并返回明确文案。

## 8. 应用身份和用户身份兼容

- 两种身份保留：不填 `userAuthorizationId` 走应用身份（tenant_access_token），填写则走用户授权（校验 grant 归属当前用户 + 当前连接 + 当前项目）。
- 事件验证仅约束用户身份；应用身份添加知识源不依赖 OAuth。UI 明确说明两者区别与适用场景。
- Token 获取路径未混用（`ConnectorOAuthTokenService` vs `feishu.tenantAccessToken`），底层刷新协议未改动。
- 知识源继续通过 `connectionId` + `userAuthorizationId` 追溯身份；切换身份不绕过 `ProjectAccessGuard` / `ProjectWriteGuard`。
