## 2. Phase 0 取证（决定接入点的事实）

| 问题 | 结论 | 证据 |
| --- | --- | --- |
| 谁在调 rerank？ | 生产默认走 `SemanticHeuristicReranker`（`PipelineConfig.defaultConfig()` 的 `LEXICAL_HEURISTIC`）；`NEURAL_MODEL` **没有任何生产调用方** | 全仓 grep；`RerankerType` 仅注册表出现 |
| `NeuralModelReranker` 能用吗？ | **不能**：它构造 `ChatCompletionCommand` 时 `callerUserId=null`，`RoutingChatModelGateway.resolveProvider` 直接抛 `AI_PROVIDER_UNAVAILABLE` → 永远降级 | `NeuralModelReranker.java:112-123`、`RoutingChatModelGateway.java:169-172` |
| 候选从哪来？ | 检索管线（Dense + Lexical → RRF → 窗口/父子扩展）后的 `List<RetrievalCandidate>`；知识问答走 `ProjectKnowledgeRetrieval` 的 `DENSE_LEGACY`，**不经过 rerank**；只有 Agent 的 `search_project_knowledge`（RAG_V2）会进管线 | `KnowledgeQuestionApplicationService:109`、`KnowledgeSearchAgentTool:108` |
| 分数怎么用？ | `withRerank(score, name)` 写入 `rerankScore`，按 score→rrf→id 稳定排序，再截 `finalTopN`；证据字段不可变 | `NeuralModelReranker.doNeuralRerank`、`SemanticHeuristicReranker.doRerank` |
| 现有指标/日志？ | 只有 `log.info/warn`，无 Micrometer 指标 | 两份 reranker 全文 |
| Java 有内部模型网关吗？ | **没有**；Python 无密钥无法调模型 | `src/main/java` 无 `/internal/ai/**` 控制器 |

**由此冻结**：`rerank.mode` 必须作用在**检索管线层**（包装当前 active reranker），Java 基线是
生产实际排序（启发式），而不是"未接线且必然降级"的 `NeuralModelReranker`；同时必须补
Java 内部模型网关，Python 才可能真正打分。

## 3. 冻结契约（落地版）

### 3.1 Python `POST /v1/rag/rerank`

请求：`{schemaVersion:1, query, topK:8, candidates:[{id,title,text}], deadlineMs:3000}`

| 约束 | 值 |
| --- | --- |
| candidates | 1–50；id 1–128 且唯一；title ≤500（可空）；text 1–2000 |
| query | 1–4000，去空白非空 |
| topK | 1–50，默认 8 |
| deadlineMs | 1–30000，默认 3000；服务端硬 deadline，超时 `DEADLINE_EXCEEDED`(504)，**不返回半成品** |
| 响应 | `{schemaVersion:1, scores:[{id,score}], modelAlias, usage}`；scores 覆盖全部输入 id、按输入序、score∈[0,1] |
| usage | `source ∈ PROVIDER/ESTIMATE/UNKNOWN`；未知时 token 为 null，不填 0 |
| 幂等 | `Idempotency-Key` 可选；同 key+同 body 10 分钟逐字节重放（有界 1024，只缓存成功）；同 key 不同 body → 400 |
| 鉴权 | `Authorization: Bearer <服务令牌>`；未配置令牌 fail-closed（503），测试可用 `AI_WORKER_ALLOW_INSECURE_INTERNAL=true` 显式放行 |
| 错误码 | 复用 P0 的 9 码；模型输出不可解析 → `SCHEMA_VIOLATION`(422) |

### 3.2 Python → Java 内部模型网关

`POST /internal/ai/v1/model-calls`：
`{schemaVersion, purpose:"KNOWLEDGE_CHAT", systemPrompt, userPrompt, outputFormat:"PROMPT_JSON", deadlineMs, callId}`
→ `{schemaVersion:1, content, usage{inputTokens,outputTokens,source}, modelAlias, latencyMs}`。

- 鉴权：静态 Bearer（`RERANK_SERVICE_TOKEN` 两端同值），常量时间比较，未配置 fail-closed；
- 服务账号：`rerank.model-user-id`（现有 `ChatModelGateway` 必须非空 `callerUserId`），登记遗留；
- **`PROMPT_JSON` 而非 `JSON_OBJECT`**：staging 供应商无 `STRUCTURED_OUTPUT`，否则必拒（见 §7.2）。

### 3.3 Java `rerank.mode`

| 值 | 行为 |
| --- | --- |
| `java`（默认） | 薄包装：只记 `rerank.calls{mode=java}` 与延迟，结果对象原样返回；零 Python 调用 |
| `shadow` | **先返回 Java 结果**；Python 对比提交到虚拟线程 + 信号量 8 的有界后台；饱和记 `skipped`；只记 overlap/score delta/failure/latency |
| `python` | 同步调 worker；成功按 Python 分数排序；失败（超时/5xx/非法/缺 id）→ Java 启发式 + `PARTIAL_SCORE`/`degraded`；**请求绝不失败** |

仅对 `rerankerType != PASS_THROUGH` 生效（Dense-only 的"不重排"语义不得改写）。
幂等键 = `sha256(projectId + "|" + 完整序列化 body)[0:32]`，重试不变；`X-Call-Id` 带 attempt；
只对连接失败/502/503 重试 ≤2 次；**504 不重试**（deadline 已耗尽）。

## 4. 评测口径与结果

### 4.1 冻结集

`ai-collab-ai-worker/tests/fixtures/rerank_set/rerank_baseline.v1.jsonl`：15 条中文合成语料，
每条 6–10 候选、graded 相关度 0/1/2、`supports` 与标签一致；**不含生产数据**。
指纹：`sha256=f5baa744…`、19704 字节、15 cases。

| 指标 | 口径 |
| --- | --- |
| NDCG@8 | gain `2^rel-1`、discount `log2(rank+1)`、IDCG 理想排序、逐 case 平均 |
| 引用支持率 | top-8 中 `supports=true` 条数 / `min(8, 候选数)`，逐 case 平均 |
| P95 | 最近秩法（整数 `ceil(95n/100)`），不做插值 |

### 4.2 结果

| 路径 | NDCG@8 | 支持率 | P95 |
| --- | --- | --- | --- |
| Java 启发式（生产基线；Python 复刻，15/15 排序逐位一致） | **0.9614184** | **0.5361111** | 0.13–0.15ms（纯内存，270 样本） |
| Python rerank + 真实 ModelScope `DeepSeek-V4.1-Flash-1017` | **0.9791335** | **0.5361111** | **5054.30ms**（15 样本，deadline 10s） |

- **NDCG 提升 1.8%**，支持率持平；与 staging shadow 的 top-8 重合率 1.0 互相印证：
  候选集合不变、分数排序更接近标注。
- 跨语言一致性：`RerankParityWithPythonTest` 把 Java `SemanticHeuristicReranker` 的 top-8
  与 Python `ai-eval --scorer heuristic` 的 15 条 ranking 逐位比对，全部相等；NDCG 差 ≤1e-9。
- 真实模型结果文件 `sha256=f9f8d1b5…`（staging `/tmp/rerank-eval-worker.json`）。

### 4.3 P95 口径与结论

| 口径 | 值 | 结论 |
| --- | --- | --- |
| `worker-overhead`（不含模型，端点/解析/打分） | 未单独测量（模型占绝对主导，worker 内部耗时直方图 25–50ms 档） | **NOT_VERIFIED** |
| `worker-e2e`（含真实模型） | **P95 5054ms**（15 样本） | **NOT_MET**（门禁 800ms） |

单次直连模型调用实测：8 候选×400 字符 Prompt，P50≈2.0s（1.85–2.7s）；
9 候选时多次触达 3s deadline。**结论：在本环境/本模型下 800ms e2e 不可达**，不通过修改门禁或
缩减候选来"凑绿"；若要满足门禁，需换更低延迟模型/专用推理端点，或把 rerank 限定在 shadow
（用户不可见）。该结论已写进冻结文档 §4 与 §7。

### 5.3 过程中修复的 3 个真实缺陷（单测未覆盖，staging 暴露）

1. `RerankGatewayClient` 有两个构造器且无 `@Autowired` → Spring 选默认构造器，**应用启动失败**；

## 6. 为什么（关键决策）

1. **接入点选管线层，而不是 `NeuralModelReranker`**：后者是"未选中 + 必然降级"的死路径，
   在它上面做 shadow 只能证明死代码没变，不能证明生产排序变化。
2. **Java 基线 = 启发式**：这是生产实际排序；用它算 NDCG 才有对照意义。
3. **shadow 非阻塞**：真实模型 P50≈2s，若同步等待会把每个请求的 P95 翻倍，
   违背"shadow 零行为变化"。因此先返回 Java 结果，Python 在后台有界执行。
4. **幂等键覆盖完整 body**：只哈希 id 会在文档重建后命中 10 分钟前的旧分数。
5. **504 不重试**：deadline 已耗尽，同 deadline 重试不可能成功，只会放大用户等待。
6. **服务账号是临时方案**：现有 `ChatModelGateway` 必须有 `callerUserId`；用
   `rerank.model-user-id` 让 Python 的模型调用落在服务账号下，W4 换系统共享模型档案。
7. **800ms 拆双口径**：不把"模型延迟"与"服务开销"混在一个数字里，也不改门禁数值。

## 8. staging 环境的重要限定（必须与结论一起读）

1. **嵌入模型是测试替身**：staging 没有可用的 Embedding Provider（ModelScope 不提供
   embeddings，Ollama 镜像在 16G 根盘装不下）。为打通"文档 → 检索 → rerank"链路，
   部署了一个**确定性哈希 bag-of-words 嵌入服务**（768 维，OLLAMA 协议，仅内网）。
   因此 staging 的**检索质量与引用支持率不代表生产**；本报告的 NDCG/支持率来自
   **冻结集 + 真实 rerank 模型**，与这个替身无关。
2. **没有真实用户流量**：dev-staging 过去 24h 仅 2 条请求；canary 的"流量"是 4 个并行
   Agent 会话，属**合成流量**。真实 canary 需在有真实用户的 staging/生产环境另行执行，
   本波标 `NOT_CLAIMED`。
3. **模型延迟方差大**：同一 Prompt 在 1.85–5s 间波动；P95 样本仅 15，置信度有限。

## 10. 回滚语义

- **运行期回滚**：`RERANK_MODE=java` + 重启 app。java 模式不访问 worker，行为与迁移前等价。
- **部署回滚**：回滚镜像必须用**含 V90 的 W3 版本**；不能回退到 J1 镜像（J1 不认识 V90，
  Flyway 校验会失败）。已在 runbook §4 写明。
- **worker 故障**：shadow 只记失败；python 模式单次 deadline（3s）后回退，请求不失败。
- **内部网关故障**：worker 返回 503，Java 回退；`rerank.mode=java` 完全不受影响。

## 11. 遗留与风险

| # | 遗留 | 影响 | 后续 |
| --- | --- | --- | --- |
| 1 | **§7.8 Ed25519 5 分钟短令牌未实现** | 静态长期 Bearer，无 scope/轮换；靠内网 + fail-closed 兜底 | W4 前补签发/验签与轮换 |

| 3 | **P95 e2e 5.05s > 800ms** | python 模式直接进用户路径会显著变慢 | 换低延迟模型；或长期只开 shadow；或把 rerank 移出关键路径 |
| 4 | 真实用户 canary 未做 | 无法证明真实分布下的质量/延迟 | 在有流量的 staging 跑 `shadow` ≥1 周再评估 |
| 5 | staging 嵌入是测试替身 | 检索质量不代表生产 | 生产接真实 Embedding；staging 换可用 Provider |
| 6 | 无熔断器 | worker 挂起时 python 模式每次等 3s（已不重试） | 加 circuit breaker / 半开 |
| 7 | 内部端点无限流/审计 | 内网可信 + 令牌；无 per-caller 配额 | 与 §7.8 一起补 |
| 8 | 幂等缓存进程内、每副本独立 | 多副本下同 key 可能各调一次模型 | 若上多副本，改共享缓存或接受重复 |
| 9 | NDCG 冻结集仅 15 条 | 统计置信度有限，标签为合成标注 | 扩集 + 人工复核；holdout 不参与调参 |
| 10 | shadow 每次检索多一次模型调用 | 成本增加；并发 8 上限 | 按项目/比例采样，或只在观察期开 |
