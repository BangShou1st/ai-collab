## 三、两个工作包各自的原始故障

### 1. P4.2-A：文档下载链路原始故障
- **Staging 远程预签名签名失配**：在 InstaBox Staging 真实环境中，文档上传正常，但尝试通过前端下载文档时，MinIO 抛出 HTTP 403 Forbidden (`SignatureDoesNotMatch`)，签名验证失败。
- **动态端口与网关端口冲突**：此前修复提交（`e33c3f3`）尝试将 Nginx `proxy_set_header Host` 设为 `$host`，导致本地或动态端口映射（如 `127.0.0.1:44747`）下的端口被无差别剥离，造成测试环境签名失败；而在 Staging 环境中，外部网关终止 TLS 后向宿主机转发请求带有 `:8443` 端口，导致 MinIO 收到的 Host 与客户端签名的 Host 出现偏差。
- **静态托管断流**：若前端托管在 Cloudflare Pages 等无服务器边缘节点，缺少同源 `/storage/*` 转发规则，用户请求直接命中 SPA fallback 返回 HTML，导致下载中断。
- **单一通道脆弱性**：此前下载完全依赖客户端重定向预签名 URL，一旦客户端与存储网关间存在代理层篡改或复杂网络限制，缺乏后端受控的直接安全下载备选路径。

### 2. P4.2-B：Agent 部署配置机制原始故障
- **Compose 配置硬编码**：`compose.staging.yml` 和 `compose.prod.yml` 中均将 `CHAT_ENABLED` 与 `AGENT_ENABLED` 静态写死为 `"false"`，即使运维人员在 `.env` 中声明 `AGENT_ENABLED=true`，也会被 Compose 配置静默覆盖，导致 Agent Worker 无法在容器环境中按需启动。
- **配置一致性与校验断层**：环境变量示例 `prod.env.example` 缺少 `CHAT_ENABLED`、`AGENT_ENABLED` 以及 `AGENT_MCP_ALLOWED_HOSTS` 的完整说明；部署前预检工具 `prod-config-check.mjs` 未对这些变量进行格式校验，存在配置错误被静默忽略的安全隐患。
- **MCP 白名单策略未明确**：当 `AGENT_MCP_ALLOWED_HOSTS` 未配置或为空时，缺乏部署级明确策略与格式检查，需验证其默认安全边界。

## 四、根因分析

### 1. P4.2-A 根因分析
1. **SigV4 规范头一致性冲突**：
   - AWS S3 / MinIO 采用 SigV4 预签名认证。预签名 URL 由后端根据 `MINIO_PUBLIC_ENDPOINT`（如 `https://8443-...instabox.tech`）计算，其 Canonical Request 的 `Host` 头为 `8443-...instabox.tech`（标准 443 端口，不含端口号）。
   - 客户端经由公网网关请求时，网关在盒内转发给宿主机 `8443` 端口，上游发送的请求头变为 `Host: 8443-...instabox.tech:8443`。
   - 当 Nginx 原样反代时，MinIO 计算的签名头包含了 `:8443`，导致签名失配；而若盲目采用 Nginx 内置变量 `$host`，在测试容器或非 8443 自定义端口场景下，端口又会被错误剥离。
2. **Nginx location 内 if 正则陷阱**：
   - 在 Nginx `location` 内部使用 `if ($forward_host ~ ^(.+):8443$)` 会触发 Nginx 的 "if is evil" 隐式上下文重写，破坏 URI rewrite 逻辑并返回 400 Bad Request。必须改在 `http` 块顶层使用声明式 `map` 统一归一化。
3. **架构安全防嗅探原则**：
   - 后端 `ProjectAccessGuard.requireMember` 在访问未授权项目或不存在的项目时，统一返回 404 Not Found（防信息嗅探）。原有集成测试断言 403 导致断言偏离设计预期。

### 2. P4.2-B 根因分析
1. **Docker Compose 变量层级覆盖**：
   - Compose 文件中定义的环境变量如果显式声明为字面量（如 `AGENT_ENABLED: "false"`），其优先级高于 `.env` 文件中的同名变量，导致外部环境配置失效。
2. **缺失配置约束边界**：
   - 生产部署校验脚本 `prod-config-check.mjs` 仅校验了数据库与基础密钥，未覆盖 AI/Agent 运行时开关与网络策略，导致部署运维无法在上线前发现配置疏漏。

## 六、关键代码修改说明

### 1. Nginx 顶层 Map 标准化 Host 头
在 `ai-collab-deploy/nginx/staging.conf` 顶层增加两级 `map` 映射，消除 location 内的正则，避免请求被重定向破坏：
```nginx
# 优先取 X-Forwarded-Host，兜底使用 HTTP Host
map $http_x_forwarded_host $storage_forward_raw {
    default $http_x_forwarded_host;
    ""      $http_host;
}

# 若网关附加了 :8443 端口，剥离端口还原为公网签名 Host；其他测试端口保持原样
map $storage_forward_raw $storage_forward_host {
    ~^(?<h>[^:]+):8443$ $h;
    default             $storage_forward_raw;
}
```

### 2. 后端直接流式下载端点实现
在 `DocumentController` 中实现直接下载端点，满足不暴露 MinIO 凭据、严格权限防嗅探及标准 RFC 5987 / RFC 6266 中文文件名支持：
```java
@GetMapping("/{documentId}/download")
public ResponseEntity<InputStreamResource> downloadDocument(
        @PathVariable String projectId,
        @PathVariable String documentId,
        @AuthenticationPrincipal AuthenticatedUser user) {
    DocumentDownloadResource res = documentApplicationService.download(projectId, documentId, user.userId());
    String encodedFilename = URLEncoder.encode(res.filename(), StandardCharsets.UTF_8).replace("+", "%20");
    HttpHeaders headers = new HttpHeaders();
    headers.add(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"" + encodedFilename + "\"; filename*=UTF-8''" + encodedFilename);
    headers.setContentType(MediaType.parseMediaType(res.contentType()));
    if (res.sizeBytes() > 0) {
        headers.setContentLength(res.sizeBytes());
    }
    return ResponseEntity.ok().headers(headers).body(new InputStreamResource(res.inputStream()));
}
```

### 3. Compose 与部署检查环境变量受控解耦
在 `compose.staging.yml` 与 `compose.prod.yml` 中：
```yaml
CHAT_ENABLED: "${CHAT_ENABLED:-false}"
AGENT_ENABLED: "${AGENT_ENABLED:-false}"
AGENT_MCP_ALLOWED_HOSTS: "${AGENT_MCP_ALLOWED_HOSTS:-}"
```
在 `prod-config-check.mjs` 中添加严格防御性格式检查：
```javascript
if (env.CHAT_ENABLED && !['true', 'false'].includes(env.CHAT_ENABLED.trim().toLowerCase())) {
  throw new Error(`CHAT_ENABLED 必须为 'true' 或 'false'`);
}
if (env.AGENT_MCP_ALLOWED_HOSTS) {
  const hosts = env.AGENT_MCP_ALLOWED_HOSTS.split(',').map(s => s.trim()).filter(Boolean);
  const hostRegex = /^(?:[a-zA-Z0-9-]+\.)+[a-zA-Z]{2,}$|^\d{1,3}(?:\.\d{1,3}){3}$|^localhost$/;
  for (const h of hosts) {
    if (!hostRegex.test(h)) {
      throw new Error(`AGENT_MCP_ALLOWED_HOSTS 包含无效的主机格式: ${h}`);
    }
  }
}
```

## 十二、Staging 部署注意事项

1. **环境变量配置要求**：
   - 默认部署下，Agent 维持关闭（`AGENT_ENABLED=false`）；
   - 若需在 Staging 开启 Agent 验证，请在部署环境变量（`.env`）中显式指定：
     ```bash
     CHAT_ENABLED=true
     AGENT_ENABLED=true
     AGENT_MCP_ALLOWED_HOSTS=
     ```
2. **MCP 安全策略**：
   - 当 `AGENT_MCP_ALLOWED_HOSTS` 留空时，后端 `McpEndpointPolicy` 默认拒绝所有外部 MCP 主机连接（抛出 `AGENT_MCP_ENDPOINT_FORBIDDEN`），此为预期安全边界。若需接入外部 MCP 服务，必须逐个配置合法的主机名或 IP。
3. **Nginx 配置更新**：
   - 部署更新时需触发 Nginx 容器重载配置（`docker compose ... restart nginx`），确保新的 `map` 变量生效。

## 十三、剩余风险

1. **极超大文件下载内存与连接开销**：
   - 直接流式下载端点采用 `InputStreamResource` 逐块写出响应流，不占用堆内存；但在海量高并发同时下载超大附件（如 > 500MB）场景下，长连接可能会占用 Spring Boot 工作线程。推荐大文件仍优先利用修复后的预签名直连下载。
2. **外部多层反向代理 Host 透传规范**：
   - 若客户自建 CDN 或外部网关，需确保正确传递 `X-Forwarded-Host` 及 `X-Forwarded-Proto`，以保证签名及链接解析的一致性。
