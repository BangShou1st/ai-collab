## 1. J1-1 Legacy 退出：BLOCKED（不删）

### 1.1 触发条件与可达性（有证据）

- Legacy 分支判定：`RoutingAgentModelExecutor.ResolvedRequest.of`
  （`agent/application/runtime/RoutingAgentModelExecutor.java:58-63`）
  `legacyMode = !capabilities.contains(NATIVE_TOOLS) && capabilities.contains(CHAT)`。
- 配置来源：`AgentModelConfigurationStore.require`
  （`AgentModelConfigurationStore.java:20-42`）→ `providers.resolve(requesterId, AGENT)`；
  **只校验 `enabled()`，不校验能力**。
- 分配接口同样不校验能力：`UserAiProviderService.assignPurpose`（`:147-181`）只查
  "存在 / 启用 / 共享已发布"。
- 前端用途选择器不按能力过滤：`UserAiSettingsView.vue:133`（`customProviders.filter(c => c.enabled)`），
  只在 `:418-426` 显示"未启用所需能力"角标，不拦截。
- **新建自定义 provider 的默认能力就是 CHAT-only**：`provider-profiles.ts:56`
  `= ['CHAT','STREAMING']`；DB 列默认 `'CHAT,STREAMING,USAGE'`
  （`V39__create_user_ai_configuration.sql:17`、`V77__shared_ai_provider_and_admin_system.sql:18`）。
- 唯一 NATIVE_TOOLS 硬门控在 `RoutingModelTurnGateway.java:96-98`，而 Legacy 走
  `ChatModelGateway`（`LegacyReadOnlyAgentExecutor.java:80-91`）→ **绕过该门控**。

结论：用户可以在"新建自定义模型（不勾工具调用）→ 用途选 Agent → 提交 Agent 任务"这条
**零拦截**链路上真实进入 Legacy 执行器。

### 1.2 为什么仍不能删（两条独立理由）

**理由 A：缺"CHAT-only 真实调用量为 0"的证据（设计 §5.1/§5.3 前置）。**

- `agent.model.request` 指标只有 `purpose` / `outcome` 两个 tag
  （`AgentRuntimeMetrics.java:68-69`）；`MODEL_STARTED` 事件、`agent.model.turn` span、
  gauge 均无模式字段；`LegacyReadOnlyAgentExecutor` 声明了 logger 但全文未使用。
- `LegacyDecisionParseFailure` 在 `AgentRuntimeMetrics.java:74` 被归入 `invalid_response`，
  与 native 不可区分。
- 仅有两个**可落库原始字段**可离线统计：
  - `agent_tool_invocation.source_mode`（V59，仅覆盖"有工具调用"的轮次）；
  - `agent_run.model_configuration_snapshot->>'mode'`（V51）——但
    `AgentModelConfigurationStore.java:38-39` 对 `isPreset()`（含 `presetCode` 以
    `SHARED` 开头的共享配置）**一律写 NATIVE_TOOLS**，会漏计共享 CHAT-only 行。
- 因此仓库内无法证明"用量为 0"，需要生产库 SQL（见 §1.4）。

**理由 B：删除会破坏一条安全边界（不是缺证据，而是"删了会坏"）。**

- `AgentToolCallExecutor.validateToolCall`（`:610-620`）在恢复批次用
  `source_mode` 判定旧轮次是否只读：`"LEGACY_READ_ONLY".equals(sourceMode)`，
  **为 null 时回退 `modelExecutor.isLegacyModeForRun(run)`**（`:613-614`）。
- 该 null 兜底覆盖 V59 之前的历史行；若随分支删除且不补保守拒绝逻辑，历史 Legacy 轮次的
  待处理写调用会被放行进入提案/执行路径。V59 只加了可空列，**无 CHECK 约束**
  （`V59__agent_invocation_source_mode.sql:4`）。
- 设计 §5.3 要求"删代码与删配置分开两次发布"，本批不具备该前提。

### 1.3 不删之后仍成立的现状

- 无定时任务创建 Agent Run（`createRun` 仅 `AgentRunService.submit` 一个调用方）；
  但调度器每轮重解析配置，**在途 Run 会随用户把 AGENT 切成 CHAT-only 而进入 Legacy**
  （`AgentModelConfigurationStore.java:27`）——所以"没有定时任务"不能证明用量为 0。
- "CHAT-only 仅作普通对话"已是既有事实：知识问答/规划本就走 `ChatModelGateway`
  （`KnowledgeQuestionApplicationService.java:65,156-159`、`TaskPlanModelClient.java:24`），
  与 Agent Run 无关。

### 1.4 解除阻断的最小动作（按序，全部不删代码）

1. **统计（生产库，一次查询）**：

```sql
-- (a) AGENT 用途指向 CHAT-only 的配置行：准确口径
SELECT p.id, p.name, p.model_name, p.capabilities
FROM user_model_purpose_assignment a
JOIN user_ai_provider p ON p.id = a.provider_id
WHERE a.purpose = 'AGENT' AND p.capabilities NOT LIKE '%NATIVE_TOOLS%';

-- (b) 历史 legacy 轮次与 V59 前无来源行
SELECT count(*) FILTER (WHERE source_mode = 'LEGACY_READ_ONLY') AS legacy,
       count(*) FILTER (WHERE source_mode IS NULL)             AS pre_v59,
       count(*)                                                AS total
FROM agent_tool_invocation;

-- (c) 上界参考（会漏计共享 CHAT-only 行，不能单独作准）
SELECT count(*) FROM agent_run WHERE model_configuration_snapshot->>'mode' = 'LEGACY_READ_ONLY';
```

2. **让"新 legacy 轮次"归零并可观测**（一个发布）：给 `agent.model.request` 增加
   `mode` tag（由 `resolved.legacyMode()` 传入）；在 Agent 入口按
   `RoutingModelTurnGateway` 同口径快速失败并给可操作配置提示；同时决定"新建 provider
   默认能力"与"AGENT 用途是否按能力过滤"。
3. **配置迁移 + 用户通知**（单独一次发布，新增迁移；不在本批）。
4. **第二个周期**才删 `LegacyReadOnlyAgentExecutor`、`AgentDecisionParser`、
   `LegacyDecisionParseFailure`、`RoutingAgentModelExecutor` 的 Legacy 分支，并把
   `source_mode IS NULL` 改为保守拒绝。

影响面清单（供后续批次直接使用）：

- 可直接删：上述 3 类 + `AgentRuntimeConfiguration.java:33-36` 的 parser Bean +
  `RoutingAgentModelExecutor.java:34/40/44/55/59-62/103-108/119-131` +
  `AgentModelMessageComposer.java:820-828`；
  测试 16 个用例（`LegacyReadOnlyAgentExecutorTest` 8、`PresetAwareRoutingTest:65` 1、
  `RoutingAgentModelExecutorRequestConsistencyTest:104` 1、`AgentRuntimeDomainTest`
  3 个 parser 用例、`AgentRuntimeBehaviorTest:419` 1、`AgentRuntimeCoordinatorTest:867` 1、
  `AgentContextReliabilityD1D8RegressionTest:388` 1）。
- 需改写（拿 Legacy 当夹具）：`AgentModelConfigurationSwitchPostgresIntegrationTest:211/246`、
  `PersistedModelTurnRecoveryPostgresTest:863`、`AgentRuntimeRequestSnapshotTest:88/117`、
  `AgentModelMessageComposerRequestConsistencyTest:53/66/74/87`、
  `AgentContextReliabilityD1D8RegressionTest:688`。

## 2. J1-2 文档范围结构化：BLOCKED（不删正则）

### 2.1 前置条件核对（任务要求"前端已有选择器且请求/工具只接受显式 documentIds"）

| 入口 | 前端选择器 | 请求字段 | 后端消费 | 结论 |
| --- | --- | --- | --- | --- |
| 知识问答（流式） | 有，多选上限 20 且仅 READY（`KnowledgeView.vue:99-118`、`use-knowledge-view.ts:61`） | `{question, documentIds}` 恒发（`knowledge-api.ts:83`） | `KnowledgeQuestionRequest` → service 校验 ≤20/去重（`KnowledgeQuestionApplicationService.java:230-240`） | 就绪 |
| 规划 | 有，多选上限 10（`PlanningView.vue:325`） | `form.documentIds`（`use-planning-view.ts:99`） | `CreateTaskPlanRequest.documentIds`（`@Size(max=10)`）→ 落库 → 检索（`TaskPlanContextAssembler.java:47-52`） | 就绪 |
| **Agent 检索/正文工具** | **无文档范围选择器**（只有单文档页面上下文 `selectedDocumentId`，`types.ts:83`、`use-agent-workspace.ts:465`；`SubmitAgentMessageRequest` 无 documentIds） | Agent Run 请求无 documentIds | `KnowledgeSearchAgentTool:84-102`、`DocumentAgentTools:33/70-77` **依赖 `resolveUserDocumentScope` 的中文正则** | **未就绪** |

### 2.2 为什么不能先删后端正则

- 正则只在 scope 路径，不在 `search()`：`DocumentSearchService.java:31-44`（
  `LIMITED_SOURCE_LIST` / `EXCLUDED_SOURCE_LIST`）、`parseScopeIntent:147-152`，
  唯一调用者 `resolveUserDocumentScope:107-145`；`search():53-81` 不含范围解析。
- 生产消费方只有 3 处：`KnowledgeSearchAgentTool:84-85`（经门面）、
  `DocumentAgentTools:33`（`list_project_documents` 过滤）、`:70-77`
  （`get_document_outline` / `read_document_section` 越界拦截）；门面转发
  `ProjectKnowledgeRetrieval.java:119-125`（`TODO(J1)` 在 `:123`）。
- 知识问答/流式/规划**从不调用**该路径，因此删正则对它们是零影响——真正的风险全部落在
  Agent 侧：删掉后 `resolveUserDocumentScope` 只会返回 `UNRESTRICTED`，
  `UNRESOLVED_INCOMPLETE` 的阻断语义消失 → "只根据《X》"会**静默退回全项目检索**，
  正是任务明令禁止的行为。
- Agent 页没有文档范围选择器，也没有"用户原话 → 显式 documentIds"的替代通道；
  Agent 工具 schema 虽已暴露 `documentIds`（`KnowledgeSearchAgentTool.java:64-72`），
  但模型不传时后端无任何确定性来源可约束范围。

### 2.3 缺口与解除阻断的最小动作

缺口：G1 Agent 页无文档范围选择器；G2 缺"用户原话→显式范围"替代通道；
G3 现有 `UNRESOLVED_INCOMPLETE` 阻断由正则产出，删除即静默放宽；
G4 回归用例不全（同名判定在 `DocumentSearchService.java:124-129`，匹配数≠1 即进 unresolved）。
**G4 进展（2026-11-11 追加）**：`DocumentSearchServiceScopeTest` 原本已覆盖"只根据《X》"
（`explicitOnlySourceListResolvesEveryNamedDocument`）、"排除《Y》"
（`explicitExclusionBlocksOnlyTheNamedDocument`）、"未解析《Z》"
（`oneMissingDocumentMakesMultiDocumentScopeIncompleteAndFailsClosed`），缺"同名文件"；现补
`sameNamedDocumentsStayUnresolvedAndFailClosed`：两份 READY 文档归一化后同名 → 整体
`UNRESOLVED_INCOMPLETE`、`canSearch=false`、两份都不放行，同时钉住"同一项目里无范围限定的请求
仍是 `UNRESTRICTED`"（不是把所有请求都变成待确认）。该用例**只加测试、不改实现**，是 J1-2
删除正则前的行为基线。

附带发现（登记，不在本批改）：`DocumentSearchService#resolveNamedDocumentIds` 对同名请求会返回
**全部**匹配 id（`distinct` 后不去重语义），与 `resolveUserDocumentScope` 的"多义即 unresolved"
不一致；该方法在生产代码中无调用方（仅测试引用），应在 J1-2 落地时一并删除，避免留下第二套
范围语义。

解除阻断（任选其一，需产品确认后再做）：

1. Agent 请求/页面上下文增加显式 `documentIds`（复用知识问答选择器），后端
   `AgentContextAssembler` 校验项目归属与 READY 后下发工具；或
2. 保留确定性极小解析（只识别 `《…》` token，交 `resolveNamedDocumentIds:84-100`
   精确解析），任何未解析/同名冲突走 `RequestUserInputAgentTool` 澄清（
   `RequestUserInputAgentTool.java:9-23` + `AgentToolCallExecutor.java:278-291`），
   绝不静默放宽。

届时最小安全改动：删 `DocumentSearchService.java:27-44`、`:147-173`、
`resolveUserDocumentScope` 的正则路径；保留 `search():53-81` 的项目归属 / READY /
撤权过滤（SQL 见 `DocumentMapper.java:232-249`、`:344-357`）；补
"只根据《X》/排除《Y》/同名 2 份 READY/未解析《Z》"四类回归。

- `KnowledgeQuestionChatToggleTest` 两处构造点补 provider；`capability-matrix.md` 知识问答行同步。

### 4.3 为什么"生产零行为变化"

1. `KnowledgePromptProvider` 是无 `@Profile`/`@Conditional*`、无 `@Bean` 工厂的裸 `@Component`，
   与两个服务同一扫描树；此前已通过 `@Autowired(required=false)` 注入成功 → 线上
   `promptProvider != null` 恒真，三元永远取 provider 分支。
2. 新代码调用同两个方法、同参数顺序，调用点仍在同一 `ChatCompletionCommand` 构造之前 →
   同一输入下出站 prompt 字符串逐字节相同。
3. 纯"删不可达分支"，唯一差异是依赖图缺 Bean 时**启动失败**而不是静默降级到弱 Prompt。
